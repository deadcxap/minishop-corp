# AGENTS.md

Точка входа для AI-агентов. Перед изменениями прочитайте
[CONTRIBUTING.md](CONTRIBUTING.md) и [ТЗ](docs/specification.md).
CONTRIBUTING.md определяет рабочий процесс и архитектурные правила, ТЗ — поведение
продукта. [План реализации](docs/implementation-plan.md) определяет этапы и их готовность.
Актуальные инструкции пользователя имеют приоритет над этими документами.

## Обязательные правила

- Пишите только в репозиторий `minishop-corp`. Соседние `remnawave-minishop` и
  `kiro-wheel` доступны только для чтения. Не изменяйте там исходники, Git-состояние,
  зависимости, кеши, результаты тестов или сборки. Стенд и временные файлы — здесь.
- Каждый завершённый связный блок изменений оформляйте отдельным коммитом после
  соответствующих проверок. Сообщения — Conventional Commits на английском;
  не добавляйте `Co-Authored-By`. Не включайте посторонние изменения пользователя.
- По текущему решению владельца все правки выполняются в `main`, пока он явно
  не укажет иное; это имеет приоритет над общим правилом веток для отклонений.
- Каждую фичу, отклоняющуюся от базового плана, начинайте в отдельной ветке
  `vibe/<feature>`. Опишите отклонение и критерии приёмки до её реализации.
  Плановая работа продолжается в текущей согласованной ветке; базовая ветка — `main`.
- Запрошенная пользователем работа уже разрешена. Эти документы не добавляют
  повторного согласования обычных правок и коммитов. Незаданные бизнес-правила
  уточняйте до зависимой реализации; независимую работу продолжайте.
- Minishop управляет подписками, тегами и сквадами. Используйте его сервисы и DAL
  через адаптер плагина. Не создавайте прямой клиент Remnawave, не правьте ядро,
  не подменяйте глобально его методы и не записывайте его таблицы сырым SQL.
- Плагин не проверяет и не ограничивает версию Remnawave. Совместимость с панелью
  определяет Minishop; плагин проверяется на совместимость с самим Minishop.
- Дата контракта абсолютная. Штатное прибавление дней не заменяет назначение срока.
  Одна общая сверка раз в 6 часов обходит нынешних участников всех контрактов порциями;
  персональных расписаний нет. Бывших участников она не затрагивает.
- После выхода или исключения выдаётся новый стандартный триал. Повтор одной
  операции не выдаёт второй триал. Истечение контракта сохраняет членство и выход
  к самостоятельной оплате; само по себе триал не выдаёт.
  По Q-02, если триал выключен или его срок неположительный, выход отключает
  корпоративный доступ без триала и оставляет возможность личной покупки.
- По Q-03 вступление требует отключённого автопродления и завершённых/отменённых
  личных платежей. Плагин проверяет это через Minishop, но сам ничего не отменяет.
  По Q-04 после исключения разрешено новое вступление по действующему приглашению.
- Не реализуйте персональный запрет покупок как будто он есть в SDK. В базовом
  плане используются предупреждение и периодическая сверка срока.
- Данные и кеш берите у Minishop; отсутствие кеша обновляйте его штатными сервисами.
  Недоступное значение не подменяйте нулём.
- Проверяйте пользователя, роль и принадлежность контракту на сервере для каждого
  действия. Корпоративный управляющий не получает глобальных прав администратора.
- Приглашения бывают одноразовыми и постоянными с лимитом. Лимит успешных вступлений,
  резервирование и повторы должны быть безопасны при одновременных запросах.
  Защита от подбора использует механизмы Minishop и политику плагина; без отдельного IP-лимита.
- Собственные таблицы имеют префикс `ext_minishop_corp_`, миграции —
  `minishop-corp.`. Применённые миграции не изменяются и не переупорядочиваются.
- Корпоративные связи не блокируют штатное удаление аккаунта, даже при выключенном
  плагине. Оно завершает членство без триала, отменяет задания и снимает роль;
  история не даёт прав повторно зарегистрированному аккаунту. Правило C-02 пересмотрено.
- Сохраняйте HTTP-конверт `{"ok": ...}`, контракт Plugin API и host API.
  Внутренние импорты Minishop сосредоточьте в адаптере и проверяйте на указанной версии ядра.
- База разработки и проверок — стабильный Minishop `v3.8.1` из `dev/minishop.json`.
  Не подменяйте её текущей dev-веткой соседнего проекта. По умолчанию используйте
  отдельный `.local/minishop`; смена базы требует проверки нового стабильного релиза.
- Типизируйте Python и исходный TypeScript. Не скрывайте ошибки типов широкими
  `Any`, `any`, `type: ignore` или выключением проверки без обоснования границы интеграции.
- Все видимые строки и сообщения ошибок локализуйте в RU и EN. UI использует
  зарегистрированные слоты и страницы; чужой DOM и глобальные CSS-селекторы не являются API.
- Не правьте собранные bundles, ZIP, хеши и manifest вручную вместо генератора.
  Не добавляйте ключи подписи, токены, реальные приглашения или данные клиентов в Git.
- GitHub Actions только собирает и сохраняет подписанный установочный пакет после
  push в ветку. Он не скачивает Minishop/kiro-wheel и не запускает тесты или стенды.
  Проверки выполняйте локально; в Actions используйте постоянный ключ из Secret.

## Проверка и отчёт

Выберите проверки по матрице CONTRIBUTING.md. Для изменений только Markdown достаточно
проверки whitespace, ссылок, формулировок и согласованности документов; не запускайте
несуществующий backend или frontend и не выдавайте планируемый CI за действующий.

В конце укажите результат, выполненные проверки, существенные ограничения и созданные
коммиты. Обновляйте статус соответствующего этапа плана; незавершённую работу не отмечайте
выполненной. Публикация и push не следуют автоматически из локального коммита.
