# Совместимость адаптера Minishop

Проверенная база — **Minishop 3.8.3**, тег `v3.8.3`, commit
`0fe3ac3abba160517538cc86e812e655d46fe55a` из [конфигурации](../dev/minishop.json).
Манифест требует Plugin API 1, frontend host API 1 и возможности `user_ui: 1`,
`ui_composition: 1` в режиме `capabilities`. Установщик проверяет их версии и
runtime, а `core_revision` сохраняет сведения о проверенной сборке без запрета
других commit. База локальных проверок остаётся закреплённой: публичные возможности
не описывают все используемые внутренние сервисы и DAL.
Плагин не проверяет версию Remnawave: протокол и совместимость с панелью определяет
Minishop. Порядок установки и ограничения — в [инструкции](installation.md).

**Полной совместимости нет: новые настройки аудиторий рассылок требуют адаптации
плагина.** Рабочий код и версия пакета в рамках аудита не изменены.

Проверен исходный опубликованный ZIP 1.1.0 с SHA-256
`abc81bda07fd1ab732e9949c2792a0935200638dfedd01b89feb826caa864d1f`.
Все 61 файл runtime совпадают с исходниками и собранным frontend, ключ издателя

### Подтверждённые несовместимости рассылок

1. **Список групп рассылок пользователя возвращает HTTP 500.** Штатный
   `GET /api/admin/users/{user_id}/broadcast-audiences` вызывает новый метод
   `user_audiences()`. Унаследованная реализация вызывает `_matching_user_ids()` напрямую,
   который не знает корпоративных целей и провайдеров, зарегистрированных
   в делегированном сервисе. Ошибка воспроизводится после загрузки корпоративного
   каталога через `audience-counts`, а также с аудиторией другого плагина.
   Отдельный сценарий с обязательным Telegram-каналом падает потому, что адаптер
   не передаёт новые `settings` базовому сервису. Это три независимых воспроизведения
   одного несогласованного расширения сервиса.
2. **Исключённый пользователь остаётся получателем корпоративной рассылки.**
   Штатный PATCH успешно сохраняет исключение в `broadcast_audience_exclusions`,
   но корпоративные `resolve_user_ids()` и `counts()` не применяют его. Проверены
   отдельный контракт и сохранённый набор контрактов: получатель остаётся
   в списке, счётчик остаётся равным 1 вместо 0. Штатная отправка использует
   именно этот resolver; исключение не защищает от доставки по этой аудитории.

Семь воспроизведений сначала запущены без ожидаемых ошибок и упали на проверках
HTTP-статуса, получателей или счётчика. В
[проверках 3.8.5](../tests/integration/test_minishop_385_compatibility.py) они
сохранены как `xfail(strict=True, raises=AssertionError)` с явными причинами.
Они **не считаются прошедшими**; после исправления адаптера их нужно перевести
в обязательные проверки. Исправление должно сохранить работу на 3.8.3/3.8.4,
делегирование чужих провайдеров и исключения для каждой выбранной аудитории.
До такого исправления обновление рабочего магазина до 3.8.5 не рекомендуется.
Оба изменения нужны в [адаптере аудиторий](../backend/minishop_corp/integration/broadcasts.py).

### Остальные проверенные изменения

- Несколько штатных целей `targets`, включая корпоративный контракт и набор
  контрактов, объединяются без повторных получателей. Создание отложенной
  рассылки через настоящий HTTP API сохраняет все цели и правильное число доставок.
- Новый worker начального автосписания с баланса не продлевает корпоративный
  доступ и не списывает средства, даже при положительном балансе и близком сроке
  окончания. Проверены новый аккаунт и переход с личной подписки; включённое
  личное автопродление по-прежнему блокирует вступление до штатного отключения.
- Незавершённый платёж нового провайдера PayHot блокирует уже принятую операцию
  вступления до отмены или завершения средствами Minishop. До этого резерв
  удерживается, корпоративный доступ не выдаётся. Это проверка платёжного
  барьера через DAL, а не внешнего шлюза PayHot.
- Штатное удаление аккаунта, назначавшего или отзывавшего роли другому аккаунту,
  очищает ссылки на инициатора и корпоративные связи без выдачи триала.
  Роль и история другого аккаунта сохраняются; загруженный плагин не требуется.
- Код выдачи триала в ядре не изменился. Проверки капчи, выходов и исключений
  версии 1.1.0 остаются обязательными; новые ошибки относятся к рассылкам.

В полной оболочке обнаружено также косметическое расхождение: заголовок плитки
«Корпоративная подписка» в настройках остаётся **12 px**, тогда как штатные плитки
3.8.5 используют **14 px**. Размер иконок и сетка совпадают, разница высоты — 2 px,
переполнения нет. Это воспроизведено в RU/EN на ширинах 375/1280; открытие страницы
и переход по приглашению работают. Нужна отдельная адаптация оформления с
сохранением прежнего вида на поддерживаемых ядрах.

## Проверка Minishop 3.8.3

Для **minishop-corp 1.1.0** реализована совместимость с включённой капчей
[Minishop v3.8.3](https://minishop.minidoc.cc/changelog/), commit
`0fe3ac3abba160517538cc86e812e655d46fe55a`. Функциональная приёмка и проверка
подписанного пакета пройдены. Ниже отдельно сохранён первоначальный аудит 1.0.1.

### Корпоративное исключение из проверки капчи

В 3.8.3 `activate_trial_subscription` проверяет капчу непосредственно внутри
сервиса, включая вызовы с `commit=False, emit_event=False`. Без подтверждения
аккаунта возвращаются `activated=False` и `trial_captcha_required`; при отсутствии
Redis — `trial_captcha_unavailable`. В 1.0.1 это оставляло членство в `leaving`,
операцию в `retry` с `minishop_corp_panel_unconfirmed`, в том числе при исключении
управляющим или администратором. До активации адаптер уже менял сквады в панели;
откат БД не отменял внешнюю запись. Для 1.0.1 капчу необходимо оставить выключенной.

В 1.1.0 [адаптер выхода](../backend/minishop_corp/integration/access.py) передаёт
`captcha_verified_payment=True` только в штатную активацию корпоративного триала.
Параметр Minishop пропускает проверку для одного вызова, сохраняя остальную процедуру.
В ядре он предназначен для оплаченного триала; использование при корпоративном
выходе — принятое исключение, а не подтверждение оплаты или официальный отдельный
API административной выдачи. При обновлении ядра требуется повторная проверка.

Право на действие и принадлежность контракту проверяются перед созданием операции;
worker проверяет её актуальность. Параметр не поступает из пользовательского API.
Плагин не создаёт платёж или Redis-подтверждение, не меняет глобальные настройки
и методы Minishop. Обычные вызовы выдачи триала для того же и других аккаунтов
сохраняют капчу. В 3.8.2 параметр отсутствует и не передаётся: адаптер проверяет
его наличие в сигнатуре метода.

Срок, лимиты, сохранение истории и повторы остаются прежними. Незавершённые операции
продолжаются с сохранённым окном триала; повтор не начинает отсчёт заново.
Если триал выключен или срок неположительный, доступ снимается без триала.

[Проверки 3.8.3](../tests/integration/test_minishop_383_compatibility.py) требуют
успешного выхода и обоих видов исключения с Redis и без него, стандартных лимитов,
отсутствия платежа и сохранения капчи обычного триала. Сбои панели до и после
активации должны сохранять операцию и её срок для повтора. Строгие `xfail` удалены.

### Остальные изменения ядра

- Автоочистка не выбирает действующие и истёкшие корпоративные подписки: их
  `provider=admin` защищает от правила неиспользованного триала. Однако управляющий
  без личной подписки и аккаунт с ещё не исполненным вступлением могут попасть
  под правило не начавших триал. Настоящий `AccountCleanupWorker` удаляет такие
  синтетические аккаунты, очищает роль, отменяет задания и освобождает резерв
  приглашения; триал не выдаётся. Корпоративные связи сами по себе не запрещают очистку.
- История очищенного триала (`0107_cleaned_trial_history`) сохраняется. Штатный
  административный сброс права позволяет выдать новый триал при корпоративном выходе.

## Minishop 3.8.2

В **minishop-corp 1.0.1** учтены два отличия от прежней базы 3.8.1:

- **Новые автоплатежи.** [Проверка платежей](../backend/minishop_corp/integration/billing.py)
  читает `ProviderMandate` через штатный `provider_mandate_dal.list_mandates`.
  Для `cryptomus_subscription`, `cispay_subscription_card` и `cispay_subscription_sbp`
  состояния `pending`, `active`, `paused`, `past_due` блокируют вступление даже при
  выключенном локальном флаге автопродления, закрытых циклах и завершённых платежах.
  Запрос ограничен текущим пользователем и одной записью. Проверка выполняется при
  подтверждении приглашения, ручном добавлении и повторно в worker перед выдачей доступа.
  Плагин ничего не отменяет: после штатной отмены в Minishop операция может продолжиться.
  Завершённые разрешения (`cancelled`, `failed`) и разрешения других пользователей
  не блокируют вступление. Настройка доступности провайдера не отключает проверку
  уже выданных разрешений на списания.
- **Отложенный приветственный бонус.** При `REFERRAL_WELCOME_BONUS_ADDS_TO_TRIAL=True`
  штатная активация триала расходует бонус даже с `emit_event=False`.
  [Адаптер выхода](../backend/minishop_corp/integration/access.py) сохраняет стандартный
  срок и отметку получения бонуса: при триале 3 дня и бонусе 7 дней пользователь получает
  3 дня и теряет бонус. **Это принятое продуктовое поведение**, а не блокер совместимости.
  Плагин не восстанавливает бонус, не добавляет его дни и не подменяет методы ядра.
  При выключенной настройке отложенный бонус этим вызовом не расходуется.

В 1.0.0 отдельные разрешения на автоплатежи ещё не проверялись. Для Minishop 3.8.2
используйте 1.0.1 или новее с подтверждённой совместимостью.
[Регрессионные тесты](../tests/integration/test_minishop_382_compatibility.py)
проверяют все 12 действующих сочетаний провайдера/состояния, завершённые разрешения,

На Minishop 3.8.1 этого модуля нет: адаптер пропускает только новую проверку,
остальные проверки платежей сохраняются. Ошибки импорта существующего модуля или
чтения разрешений не превращаются в разрешение на вступление.

## Реализованный путь

[AccessAdapter](../backend/minishop_corp/integration/access.py) получает готовый
`SubscriptionService` через `PluginContext.require_subscription_service()`. Он не
создаёт клиента панели. Доменные операции вызывают его из зарегистрированного
worker; HTTP-маршруты сохраняют намерение и возвращают состояние операции.

| Операция | Путь через Minishop |
| --- | --- |
| Чтение | DAL пользователя и подписки, текущая ссылка из штатного сервиса панели; учитываются неактивные записи и более длинная историческая подписка |
| Сверка | `reconcile_period` сравнивает данные DAL и свежий снимок через `_get_panel_user_for_entitlement_verification`; `assign_period` вызывается только при отклонении |
| Назначение | Блокировка пользователя, `require_configured` для скрытого period-тарифа, штатное создание/поиск профиля, `upsert_subscription` и `update_subscription` |
| Точная дата | Абсолютное `end_date` в модели ядра и `expireAt` в payload штатного сервиса; прошедшая дата означает `is_active=False`, `status=EXPIRED` |
| Сквады | `capture_panel_squad_overrides`, DAL переопределений, `build_effective_panel_squad_fields`; предыдущие и новые управляемые сквады не становятся ручными исключениями |
| Подтверждение | `PanelApiService.update_user_details_on_panel` и `_confirmed_panel_entitlement`, который отдельно читает сохранённый результат без кеша |
| Новый триал | Штатный административный сброс права, очистка унаследованных условий через DAL, `activate_trial_subscription(commit=False, emit_event=False)`, затем назначение сохранённого окна дат и подтверждение |

Внутренние зависимости сосредоточены в `integration/`: методы `_resolve_tariff`,
`_get_or_create_panel_user_link`, `PanelUserCreateOptions`, расчёт базовых лимитов,
премиального доступа и дополнительных устройств, `_build_panel_update_payload`,
проверка entitlement, планирование/запоминание тега и снимок управляемых сквадов.
При обновлении ядра нужно повторить весь интеграционный набор, а не только импорт SDK.

Сравнение и назначение используют общие расчёты целевых полей и лимитов Minishop.
Сверка проверяет точную дату, состояние доступа, тариф, лимиты с бонусами и
дополнительными устройствами, внешний сквад в модели ядра и панели, внутренние
сквады и тарифный тег. Порядок сквадов и допустимые ручные исключения не считаются
отклонением. Чистые функции `plan_panel_tariff_tag` и
`detect_panel_manual_internal_squads` сохраняют правила Minishop без записи
пользователя или обнаруженных переопределений во время проверки. Совпадающее
состояние не вызывает `upsert_subscription`, запись сквадов или PATCH в панель.
Если свежий снимок недоступен, операция повторяется; кеш не подтверждает отсутствие
отклонения. Защита членства и версии применяется перед проверкой и исправлением.

Для пакетной постановки адаптер `integration/worker_locks.py` читает штатную
ORM-модель `User` с `FOR UPDATE SKIP LOCKED`: DAL этой ревизии предоставляет только
блокирующий `lock_user_by_id`. Это чтение и блокировка без записи таблиц ядра.
Перед изменением доступа исполнитель по-прежнему использует штатный DAL и проверяет
аккаунт. Настоящие конкурирующие соединения проверяют пропуск занятого пользователя,
выход и изменение контракта во время вызова Minishop.

Чтение данных использует `User`, `Subscription`, `UserTelegramAvatar` только
через пакетные SELECT в адаптере, а также штатные `_users_cache`, `_devices_cache`,
`get_user_by_uuid`, `get_user_devices` и инвалидацию кеша. Ошибки обновления и
неизвестные значения не превращаются в ноль; старые данные сохраняют свою отметку.
Подробности границы и неоднозначной истории — в [данных участников](members-api.md).

Аватары читает и обновляет `_ensure_cached_telegram_avatar` из webapp Minishop:
штатный `Bot`, `get_user_telegram_avatar`, `upsert_user_telegram_avatar`, сроки кеша
и ограничения размера принадлежат ядру. Проверка возраста использует
`_telegram_avatar_is_stale`; отсутствие Bot проверяется через `get_optional_bot`.
Плагин ограничивает допустимые MIME-типы и размер готового изображения, выдаёт его
через защищённый JSON host API. Прямого клиента Telegram здесь также нет.
Тестовый HTTP-двойник заменяет только транспорт; загрузка и кеширование остаются
штатными. После загрузки заново проверяются роль и текущее членство.

Лимиты period-тарифа рассчитывает Minishop с его доплатами и переопределениями.
Корпоративное назначение записывается как административное, без фиктивного платежа,
списания, реферального начисления или продления купленных устройств. Внешний сквад
контракта сохраняется в модели Minishop до синхронизации; чтение старого значения из
панели не может затереть новое целевое значение. Настоящие ручные внутренние сквады
и ручной тег сохраняются по правилам ядра.

Новый триал снимает корпоративный тариф, его сохранённые условия и внешний сквад,
сбрасывает старые бонусы/лимиты в записи подписки и завершает дополнительные права
на устройства штатным DAL. Записи покупок, платежи, аккаунт и отдельные исторические
подписки сохраняются. Текущая запись подписки меняется — это штатная модель Minishop;
снимок корпоративных условий и аудит хранятся в собственных таблицах плагина.
Внешний сквад возвращается к настройке магазина; при отсутствии настройки снимается.
Лимит устройств триала сохраняется как штатное переопределение, чтобы generic sync
не подставил обычный `USER_HWID_DEVICE_LIMIT` вместо `TRIAL_HWID_DEVICE_LIMIT`.
Счётчики использованного трафика панели не обнуляются: действует штатная политика
сброса трафика триала. Активация отмечается ядром, событие `TrialActivatedPayload`
не рассылается, чтобы не запускать дополнительные обработчики выдачи доступа.
При ошибке создания профиля штатный сервис Minishop может уведомить администраторов,
если ему передан bot; в интеграционных тестах bot отсутствует, сообщения не отправляются.

## Повторы и ответственность вызывающего кода

`PeriodAccess` содержит тариф, внешний сквад и абсолютную дату. `TrialAccess` содержит
фиксированные начало и конец; окно создаётся один раз через `prepare_trial` из
стандартного срока настроек и сохраняется в операции. Даты требуют часовой пояс,
переводятся в UTC и приводятся к точности миллисекунд штатного протокола Minishop.

Повтор не прибавляет дни. Для уже применённого окна триала выполняется проверка/
восстановление существующего доступа, без новой активации. Повтор после истечения
этого окна не открывает доступ снова. Потерянный ответ PATCH считается успехом только
после независимого подтверждения; ответ с неподтверждёнными значениями — ошибкой.

Адаптер удерживает штатную блокировку пользователя и не выполняет commit.
`activate_trial_subscription` сам может откатить транзакцию при ошибке. Worker
изолирует этот вызов отдельной сессией с savepoint на том же соединении, сохраняя
внешние блокировки и операцию. Откат БД не отменяет уже выполненный запрос панели.

Сервис членства сохраняет авторизованную операцию, окно триала и версию условий до первого вызова.
При исполнении проверяются текущий аккаунт, членство, версия и токен аренды.
Завершение фиксируется вместе с локальными изменениями после подтверждения панели.
Сам адаптер не проверяет права контракта и поколение операции: эту границу обеспечивает
[сервис членства и очередь](membership-api.md). Уже принятые действия завершаются,
а новые действия и чтение проверяют актуальные роли.

## Явные границы

- **Выход:** `prepare_departure` выбирает новый стандартный триал либо
  `DisabledAccess`, если триал выключен или его срок неположительный. `disable_access`
  завершает доступ через DAL и штатную синхронизацию, снимает корпоративный тариф,
  тег и сквады, сохраняет аккаунт и не создаёт триал. Личная покупка остаётся доступна.
- **Вступление:** перед вступлением `validate_join` требует отключённого
  автопродления и завершённых/отменённых личных платежей. Проверяются флаг подписки,
  открытые циклы автопродления, действующие подписки Wata/RollyPay/Tribute,
  разрешения Cryptomus/CISPay в 3.8.2 и все нетерминальные состояния платежей,
  включая finalization/review и неизвестные.
  Отмена и списания не выполняются. Проверка повторяется исполнителем перед выдачей.
  В `integration/billing.py` два ограниченных ORM EXISTS-запроса читают платежи и
  циклы: общего пользовательского запроса для них в DAL нет. Изменения core-таблиц
  по-прежнему идут только через Minishop. Штатная блокировка пользователя и строк
  подписок сериализует проверку с применением платежа и переключением автопродления.
- **Гибкие квоты:** действующие или будущие `FlexibleTrafficLimit`
  сохраняют собственные квоты, которые worker применяет поверх назначенного тарифа
  или триала. В изученном DAL есть чтение и создание таких окон, но не операция их
  завершения с сохранением истории. Эти аккаунты получают
  `minishop_corp_flexible_limits_unsupported` до изменения доступа. Переход для них
  **не поддержан**; перед его включением нужен отдельный подтверждённый путь через
  Minishop. Прямой SQL, удаление платежей и обход worker не используются.
- HTTP-двойник возвращает Minishop версию `2.8.1` и моделирует ответы с UUID.
  Прогон проверяет адаптер на штатных сервисах Minishop с этой фикстурой;
  реальная панель, все варианты премиального учёта и внешние платёжные провайдеры
  им не проверены. Плагин не вводит собственных ограничений версии панели.
- При потере ответа на создание профиля повтор находит его штатным поиском.
  Minishop разрешает привязать непривязанный профиль только при совпадении Telegram
  или подтверждённого email. Если обоих нет, нужна административная сверка; плагин
  сохраняет этот отказ и не создаёт второй профиль ради обхода защиты.

Эти границы не меняют ТЗ. Они определяют доказанную область адаптера и проверки,
которые нельзя подменить успешной установкой пакета. Ошибки имеют ключи RU/EN.

Собственные ссылки на аккаунт используют `SET NULL`; триггеры закрывают членство
и отменяют задания даже без worker. Предварительный выход перед удалением не нужен.
Вызов панели отдельно от транзакции БД остаётся границей Minishop; подробности — в
[удалении аккаунтов](account-deletion.md) и [схеме хранения](storage.md).

## Проверки

[Интеграционные сценарии](../tests/integration/test_access.py) проверяют переходы
с нового аккаунта, триала, платного и истёкшего доступа; скрытый тариф; сокращение,
продление, дату в прошлом и восстановление доступа. Проверены сохранность истории,
точный повтор триала, откат БД после успешной записи панели, потерянный ответ,
ложное подтверждение PATCH, снятие корпоративных и сохранение ручных сквадов/тегов,
стандартный лимит устройств и ограничения триала, платежей и гибких квот.

В тесте настоящего `TariffTrafficWorker.traffic_period_tick` намеренно меняются лимиты
и внутренние сквады HTTP-панели: worker должен восстановить корпоративные значения
из Minishop, сохранить внешний сквад и не изменить договорную дату.

## Окружение проверок

```bash
bash scripts/integration-check.sh
```

Команда читает чистые исходники закреплённого Minishop и создаёт отдельный контейнер
с его зависимостями и зависимостями тестов из lock-файла. PostgreSQL доступен только
во внутренней сети собственного стенда. Для прогона создаётся временная база;
схема устанавливается штатным мигратором ядра. После прогона база удаляется.
Обычные сценарии изолированы внешней транзакцией и savepoint, включая вызовы ядра,
которые сами выполняют commit. Сценарии конкуренции используют разные соединения
и зафиксированные синтетические данные в той же одноразовой базе. Миграции плагина
также проходят штатный runner: откат DDL и истории,
применение с нуля и повтор без изменений.

Заменён только внешний HTTP-сервер панели. `PanelApiService`, выбор версии протокола,
проверка сохранённого результата отдельным GET, DAL и бизнес-логика Minishop настоящие.
Двойник отвечает на штатный запрос Minishop к `/system/metadata` версией `2.8.1`
и моделирует ответы с UUID. Этот ответ нужен сервису ядра; плагин его не анализирует.
Сквозной сценарий с реальной панелью этим прогоном не проверяется.

Обычный `scripts/check.sh` не собирает интеграционные тесты без окружения стенда.
Они запускаются локально через `scripts/integration-check.sh`; GitHub Actions только
собирает подписанный пакет. При обрыве контейнера временная база может остаться
только в локальном PostgreSQL стенда; рабочие базы не используются.

## Аудитории штатных рассылок

В Minishop 3.8.1–3.8.2 `AudienceProvider` регистрирует фиксированные цели,
а редактор принимает один `target`. Для динамических корпоративных подписок адаптер
`integration/broadcasts.py` оборачивает экземпляр `AudienceSegmentationService` в
`Plugin.setup` через `PluginContext.services`. Это граница внутренних сервисов
закреплённой версии: классы и глобальные методы ядра не меняются. В `setup_web` адаптер
также передаётся в контекст Mini App штатным setter: ядро 3.8.1–3.8.2
не копирует этот сервис в отдельное webapp-приложение. Web и worker получают
свой адаптер из контейнера; каждый разрешает корпоративный target
по БД, без межпроцессного кеша, нового worker или собственного транспортного клиента.
Все обычные цели и регистрации других плагинов делегируются исходному сервису.

Аудитории имеют префиксы `minishop-corp.contract:` и `minishop-corp.selection:`.
Сохранённые наборы неизменяемы; исчезновение хотя бы одного контракта отклоняет всю
цель. Недоступные сохранённые цели остаются в каталоге с неизвестным счётчиком:
редактор 3.8.1–3.8.2 иначе заменяет отсутствующую цель на `all`. Сервер всё равно запрещает
их отправку. Прямой запрос неизвестной цели также возвращает штатный `invalid_audience`.

Frontend добавляет только слот `admin.broadcast.content` перед штатным редактором.
Новая вкладка с `broadcast_target` получает свежий каталог и сохраняет существующий
черновик; чужой DOM и browser storage не меняются. При смене базы нужно повторить
проверки внедрения сервиса в оба процесса, discovery, расписания, удаления цели и
этого перехода. Полная доставка, повторы и восстановление сообщений остаются
ответственностью штатного модуля Minishop.
