# Приёмка S10

Проверки **0.1.3** с сохранением формы, календарной датой, необязательным сквадом
и точным выбором управляющего описаны в [исправлениях формы](admin-usability.md).

Дополнительная приёмка **0.1.2** с новым поведением штатного удаления аккаунтов
описана в [решении C-02](account-deletion.md). Предварительный выход и переназначение
управляющего больше не требуются. Исторические результаты ниже относятся к 0.1.0/0.1.1.

Повторная приёмка кандидата **0.1.1** на стабильном Minishop **3.8.1** отражена
в [отчёте перехода](minishop-3.8.1.md). Ниже сохранён исходный результат S10.

Дата локальной проверки: 2026-10-08. Кандидат: 0.1.0. Проверяемая ревизия Minishop —
`507563b06a564a26ecb10cd4c249dcd588cbff05`; исходники kiro-wheel —
`3c6f3c7ecf37a0847841aa6ee908c03e9a8f0992`. Оба соседних репозитория доступны только
для чтения. PostgreSQL, Redis, подписи, runtime и временные файлы находятся в области
этого проекта. Проверки не обращаются к клиентской базе или рабочей панели.

## Выполняемые команды

```bash
bash scripts/check.sh
bash scripts/integration-check.sh
bash scripts/package.sh init-key  # только если ключ ещё не создан
bash scripts/package.sh build
bash scripts/package-check.sh
bash scripts/stand.sh up
bash scripts/stand.sh check
bash scripts/browser-check.sh
bash scripts/core-ui-check.sh
bash scripts/stand.sh down
```

Фактический итоговый результат: **17 Python unit-тестов, 212 интеграционных,
27 DOM и 48 браузерных сценариев** (40 в preview, 8 в полной оболочке ядра).
Ruff, строгий mypy backend (44 модуля) и сборочных модулей, TypeScript, frontend build,
wheel с локалями, native smoke, shell/YAML и ссылки Markdown проверены.
194 ключа RU/EN совпадают. Повторные сборки издателя дали одинаковый ZIP; хеши payload
dev-пакета и пакета издателя совпали. Проверены подпись, отказ при подмене файла/подписи
и другой ревизии ядра; приватный ключ отсутствует в payload.

Локальные журналы: `.local/s10-check.log`, `.local/s10-integration.log`,
`.local/s10-browser.log`, `.local/s10-package-check.log`, `.local/s10-core-ui-check.log`.
Подписанный кандидат и индекс — в `dist/release/`; хеш архива — в `SHA256SUMS` рядом.

`package-check.sh` создаёт уникальный каталог `.local/package-check/<run>/`, отдельный
Compose-проект `minishop-corp-package`, свежие PostgreSQL/Redis и plugin store. Через
настоящий HTTP API проверяет: предварительный просмотр, отказ недоверенному издателю,
доверие ключу, установку, включение, четыре миграции, выключение/включение, обновление,
повтор установки, возврат к кандидату, удаление и повторную установку с сохранением
контракта, приглашения и истории членства. Backend и worker должны перейти на одно
поколение и стать доступны. Контейнеры удаляются после проверки; данные и `host.log`
остаются для разбора. Эти экземпляры PostgreSQL не публикуют порты на хост.

Следующая версия в этом тесте — **синтетическая**: текущий payload, новый номер и
подписанная отметка `metadata/acceptance.txt`. Она не поставляется. Переход схемы с
ранних миграций на актуальные отдельно проверен в `test_sweeps.py`. Настоящего
предыдущего публичного релиза плагина пока нет.

`test_acceptance.py` вызывает функцию выдачи дней из закреплённых исходников
kiro-wheel, затем штатную синхронизацию ядра и корпоративную сверку. Это проверка
сосуществования подписок; полноценный UI колеса не запускается. Два других сценария
создают отдельный Python-процесс, фиксируют аренду задания, завершают его через SIGKILL
и исполняют вступление/выход в новом процессе после истечения аренды. Время получения
новой аренды задаётся тестом; ждать две минуты в каждом прогоне не требуется.

## Оставшаяся рабочая приёмка

- C-01/C-02 не исправлены в ядре. Владелец 2026-10-08 согласовал ограничения первой
  версии и обязательную процедуру для администратора из
  [инструкции эксплуатации](installation.md). Эти сценарии остаются вне поддержки.
- В интеграционных тестах настоящие сервисы Minishop и PostgreSQL работают с
  HTTP-двойником, возвращающим Minishop версию `2.8.1` и ответы с UUID. Это описание
  фикстуры, а не требование плагина к версии Remnawave: работу с версиями панели
  выполняет Minishop. Реальная панель, все варианты премиального учёта и внешние
  платёжные провайдеры не проверены.
- Chromium загружает подписанные файлы из настоящего Minishop в изолированной
  оболочке host API; изменения через UI выполняются на синтетических ответах.
  Дополнительно 8 сценариев запускают **полную собранную оболочку Minishop** с настоящими
  API: главная без подписки, админский раздел, переход по корпоративной ссылке и
  отправка неверного кода с CSRF-проверкой. Используются отдельные синтетические аккаунты
  и session/CSRF cookies. Реальные провайдеры входа и открытие ссылок после входа в
  клиентах Telegram требуют отдельного прогона на выделенном окружении.
- Сценарии после потери ответа на создание профиля без Telegram/подтверждённого email
  требуют штатной сверки личности администратором Minishop.
- CI обновлён, но удалённый запуск, публикация, push и установка в рабочий бот
  не выполнялись. Проверены локальные команды, а не статус удалённого workflow.

Рабочий запуск требует проверки реального окружения с соблюдением согласованных
ограничений. Локальная приёмка не снимает эти пункты автоматически.
