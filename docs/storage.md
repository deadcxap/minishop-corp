# Хранилище и серверные границы

Схема S03 устанавливается штатным мигратором Minishop через `Plugin.migrations()`.
Первая ревизия — `minishop-corp.0001_initial`. DDL зафиксирован отдельно от ORM;
изменение моделей не меняет уже применённую миграцию. Отключение плагина сохраняет данные.

## Таблицы

Все имена ниже имеют префикс `ext_minishop_corp_`.

| Таблица | Назначение |
| --- | --- |
| `contracts` | Текущие условия, управляющий и номер версии |
| `revisions` | Снимки условий каждой версии и автор изменения |
| `memberships` | Текущее членство и история завершённых вступлений |
| `invitations` | Дайджест кода, тип, лимит, успешные использования, резервы, отзыв |
| `operations` | Целевое состояние, версия условий и членства, ключ повтора, попытки и аренда worker |
| `reservations` | Связь приглашения с единственной операцией и результат расходования |
| `audit` | Действие, автор, контракт и ссылки на членство/операцию без секретов |

UUID идентифицирует контракт, членство, приглашение и операцию. Версия условий —
положительное целое. Условия и новая версия сохраняются одной транзакцией;
отложенный внешний ключ проверяет наличие снимка при commit. `ends_at` — абсолютный
TIMESTAMPTZ. Состояние «истёк» вычисляется по дате и не завершает членство.

`memberships.current_user_id` уникален и ссылается на аккаунт Minishop. Он обязателен
в состояниях `pending`, `active`, `leaving`; при `left`, `excluded`, `failed` связь
освобождается, а исторический `user_id` и дата завершения сохраняются. Повторное вступление
создаёт новую запись. `generation` позволяет распознать операцию, подготовленную до
изменения членства. История сама по себе не даёт прав.

Лимит приглашения положителен, для одноразового равен одному. БД запрещает сумму
успешных использований и резервов сверх лимита. Для контракта допускается один текущий
постоянный код; отозванные сохраняются. Составные внешние ключи запрещают связывать
приглашение, участника, резерв или операцию с чужим контрактом. Согласованность счётчиков
с резервами обеспечивает транзакционный сервис S04, а не одна только эта схема.

Ключ повторного запроса — пара `(actor_user_id, request_id)`. Значение автора `0`
зарезервировано для системных операций. Для пользователя разрешена одна незавершённая
операция (`pending`, `running`, `retry`); несколько worker используют lease token.
Состояние `running` требует lease token и срок аренды. Интерфейс выполнения и проверка
актуальности перед вызовом адаптера будут реализованы в S05/S06. Наличие полей очереди
не означает, что фоновые переходы уже работают.

## Порядок блокировок

Изменения доступа в S05/S06 должны сначала брать штатные блокировки аккаунтов Minishop
в порядке `user_id`, затем контракт, членство, приглашение, операцию/резерв.
После ожидания строки читаются заново. Обработчик обновления условий блокирует новый
аккаунт управляющего, затем контракт; он не обходит всех участников под этой блокировкой.
Сверка каждого участника выполняется отдельной транзакцией. Нельзя брать блокировку
аккаунта после блокировки контракта. Ограничения БД страхуют сервисы от гонок.

## Удаление и объединение аккаунтов: C-02

Закреплённый Minishop не предоставляет предварительный хук для корпоративных связей
при удалении/объединении. Схема запрещает удаление аккаунта, который сейчас указан
управляющим или имеет текущее членство: внешние ключи `ON DELETE RESTRICT` останавливают
штатный DAL. При объединении аккаунт-источник удаляется, поэтому перенос такого
источника также отклоняется. Роль и членство не переносятся автоматически. Операция
ядра должна откатить транзакцию; эти сценарии проверены настоящим DAL на PostgreSQL.

Перед удалением или объединением такого источника нужно завершить членство штатным
корпоративным выходом и переназначить управляемые контракты. Выход появится в S05.
Бывший участник и прежний управляющий не блокируются историей. Объединение обычного
источника с корпоративным целевым аккаунтом сохраняет связи целевого аккаунта; изменения
его подписки попадают под будущую сверку S06.

Ограничение: ядро показывает свою ошибку удаления/объединения, а не корпоративное
пояснение. Штатные обработчики удаления (`users_actions.admin_user_delete_route` и
Telegram-обработчик `user_management_info`) сначала удаляют профиль панели и только
затем аккаунт в БД. В результате ограничение сохраняет корпоративные связи, но профиль
панели уже может исчезнуть. Этот сценарий отдельно воспроизведён настоящим HTTP-handler
Minishop с двойником панели: ответ 500, аккаунт/роль сохранены, профиль панели удалён.
Это проверка известного ограничения, а не успешной поддержки удаления.

Кроме того, до удаления источника merge-сервис может вызвать отмену внешнего
автопродления. Ограничение БД не откатывает внешние эффекты. Пока у аккаунта есть
корпоративные связи, удаление через админку ядра и объединение такого источника
с автопродлением не поддерживаются. Сначала нужны корпоративный выход и смена
управляющего. До промышленного запуска нужен предварительный guard со стороны
Minishop либо согласованная процедура отключения/переноса аккаунта.
Плагин не подменяет методы ядра; C-02 остаётся открытым.
