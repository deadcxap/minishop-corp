# Установка и эксплуатация

Локальный кандидат — **minishop-corp 0.1.6**. Целевая база — стабильный **Minishop 3.8.1**,
тег `v3.8.1`, commit `bc3379812b370ed4420b97338fc24fce5c87f1a6`, Plugin API 1, frontend host API 1,
Linux x86_64 и Python 3.12. Интерфейсы требуют `user_ui: 1` и `ui_composition: 1`.
Пакет использует внутренние сервисы этой ревизии, поэтому совместимость с другими
версиями Minishop не заявляется. Релизный manifest требует совпадения `core_revision`;
на сборке без `.build-commit` ядро не проверяет это совпадение — его нужно проверить
самостоятельно до установки.

Требования или отдельной проверки версии Remnawave у плагина нет. Совместимость
с панелью и выбор её протокола обеспечивает установленный Minishop. Версия панели
из локальных тестов не является условием установки плагина.

Пакет пока не опубликован. [Отчёт приёмки](acceptance.md) отделяет выполненные проверки
от проверки с рабочей панелью и Telegram. Ограничение C-01 согласовано владельцем
для первой версии; требование предварительного выхода перед удалением (C-02)
снято в 0.1.2. Сборка ZIP сама по себе не означает готовность рабочего окружения.

## Пакет из GitHub Actions

[Workflow Signed plugin package](../.github/workflows/ci.yml) запускается после push
в любую ветку. Он устанавливает только зависимости сборки плагина, собирает frontend,
подписывает пакет и сохраняет артефакт; Minishop/kiro-wheel не скачиваются, тесты и
стенды выполняются локально при разработке.

Перед первым запуском настройте в репозитории **Settings → Secrets and variables →
Actions → New repository secret** секрет `MINISHOP_CORP_SIGNING_KEY`. Значение —
base64 от **32 приватных байт Ed25519** постоянного ключа издателя. Используйте
существующий `.local/publisher/minishop-corp.key`, чтобы локальные и CI-обновления
сохраняли одного издателя. Открытый `publisher.pub` для подписи не подходит.
Если ключ ещё не создан, один раз выполните локальный `init-key` из следующего раздела.

Из корня репозитория с установленным и авторизованным GitHub CLI секрет можно передать
без вывода ключа на экран:

```bash
base64 -w0 .local/publisher/minishop-corp.key | gh secret set MINISHOP_CORP_SIGNING_KEY
```

Actions получает секрет только в шаге подписи и не сохраняет приватный ключ в файлы.
Отсутствующий, пустой или некорректный секрет останавливает сборку с ошибкой.
Не меняйте ключ между запусками: Minishop закрепляет ключ при первой установке.

После успешного push:

1. Откройте **Actions → Signed plugin package → нужный запуск → Artifacts**.
2. Скачайте `minishop-corp-<полный SHA commit>` и распакуйте внешний архив GitHub.
3. Внутри найдите `packages/minishop-corp-0.1.6.zip` и его SHA-256 в `SHA256SUMS`.
   Этот **внутренний ZIP** загружается в раздел **Плагины** Minishop.
   Внешний архив GitHub не является пакетом плагина.

Артефакт также содержит `minishop-plugin.json` и `publisher.pub`; версия и SHA-256
показаны в summary запуска. Срок хранения артефакта — 30 дней. Workflow не коммитит
сгенерированные файлы, не создаёт Release и не устанавливает пакет на бот.
Установка по URL репозитория требует отдельного размещения индекса и ZIP, описанного ниже;
URL страницы Actions сам по себе не является источником для установщика Minishop.

## Локальная подготовка и проверка пакета

Из корня этого репозитория после [настройки окружения](development.md):

```bash
# Один раз. Повтор откажет, а не заменит существующий ключ.
bash scripts/package.sh init-key

# Создаёт dist/release; повтор с теми же исходниками и ключом даёт те же байты.
bash scripts/package.sh build

# Полный цикл установки на отдельном чистом локальном Minishop.
bash scripts/package-check.sh
```

Ключ проекта находится в `.local/publisher/minishop-corp.key` с правами `0600`.
Сохраните его в защищённой резервной копии перед публикацией. Все обновления одного
издателя должны подписываться тем же ключом. Новый случайный ключ вместо утраченного
не является обычным обновлением: Minishop отклоняет такую замену. Ключ не входит
в Git, ZIP или дерево публикации. Ключ стенда `.local/package/development.key`
предназначен только для локальных тестов и не используется в Actions.

`package.sh build` проверяет версию проекта и Python entry point, ревизию и чистоту
Minishop, TypeScript, строит ESM, вычисляет хеши и Ed25519-подпись, затем вызывает
штатный `inspect_archive` через `--verify-host`. В ZIP входят только Python backend,
RU/EN и четыре собранных JS/CSS-файла. Исходные `.env`, runtime, тесты, базы, кеши
и ключи не упаковываются.
Архив не содержит своих Python-зависимостей: используются зависимости закреплённого ядра.

Самостоятельный `scripts/build-package.py build` не импортирует Minishop и не
требует его исходников. Для такой сборки нужны Python 3.12, Node 24 и постоянный ключ:

```bash
python -m pip install -r requirements-build.txt
npm ci --ignore-scripts --no-audit --no-fund
npm run build
python scripts/build-package.py build --key .local/publisher/minishop-corp.key
```

Эти команды выполняйте в собственном окружении внутри репозитория. CI передаёт ключ
через `--key-env MINISHOP_CORP_SIGNING_KEY`. Параметр `--verify-host` предназначен
только для локального окружения с закреплённым Minishop; в Actions он не используется.
Сборка следует [формату подписанного пакета Minishop](https://minishop.minidoc.cc/development/plugins/).

Результат в `dist/release/`:

- `packages/minishop-corp-0.1.6.zip` — готовый подписанный пакет;
- `minishop-plugin.json` — индекс для установщика из репозитория;
- `publisher.pub` — открытый ключ в base64;
- `SHA256SUMS` — SHA-256 ZIP для сверки.

`--output` позволяет задать другой каталог внутри репозитория. Генератор не
перезаписывает существующий ZIP той же версии другими байтами. Для локальной
проверки изменённого кандидата используйте новый каталог; для следующего выпуска
поднимите версию одновременно в `pyproject.toml` и `backend/minishop_corp/__init__.py`.
Воспроизводимость проверяется при одинаковых исходниках, ключе и закреплённом
окружении сборки; смена ключа закономерно меняет ZIP.

`dist/` игнорируется Git. Для будущей установки по URL репозитория нужно **после
решения о публикации** разместить сгенерированный `minishop-plugin.json` в его корне,
а готовый ZIP — по указанному относительному пути `packages/…zip` в том же commit.
Каталог `packages/` не игнорируется. Нельзя опубликовать только индекс или указать
вместо относительного пути ссылку на GitHub Release: изученный установщик скачивает
готовый файл из дерева репозитория и не запускает сборку. Генератор ничего не
публикует, не создаёт тегов и не выполняет push.

## Установка в Minishop

1. Проверьте ревизию Minishop, профиль runtime и работу штатных launcher-процессов
   backend/worker. Подготовьте согласованную резервную копию PostgreSQL и каталога
   данных Minishop, включая тарифы и plugin store.
2. Откройте **Плагины**, загрузите ZIP. После будущей публикации также можно указать
   репозиторий и нужную ветку/тег. Сверьте SHA-256 с результатом сборки и издателя
   `minishop-corp`; предварительный просмотр не выполняет код пакета.
3. Подтвердите установку и включите плагин. Minishop закрепит ключ издателя и
   перезапустит backend и worker на одном поколении. Дождитесь их готовности.
4. Проверьте раздел «Корпоративные подписки» у глобального администратора
   и плашку «Корпоративная подписка» в настройках обычного пользователя без подписки.
   На главной и в общей навигации отдельного пункта быть не должно.
5. Создайте проверочный контракт: название, существующий period-тариф (допускается
   скрытый), необязательный UUID внешнего сквада, дата окончания включительно.
   Дата считается по часовому поясу браузера, который указан в форме. Управляющий
   необязателен: контракт можно обслуживать только через админку. Для назначения
   используйте точный поиск по публичному ID Minishop `ms_…`, Telegram ID, @username
   или email и подтвердите найденный аккаунт.
   UUID проверяется через Minishop; каталог сквадов текущий сервис не предоставляет.
6. Выпустите приглашение и проверьте, что код/ссылка видны после повторного открытия
   списка. Пройдите предпросмотр и немедленное подтверждение без минутного ожидания,
   назначение, выход и проверьте тариф, точный срок, тег и сквады
   в штатной карточке аккаунта. Проверку на рабочей панели сначала проводите на
   выделенных тестовых аккаунтах с согласованными условиями контракта.

Управляющий входит обычным аккаунтом и открывает «Управление подписками» со страницы
корпоративной подписки в настройках.
Глобальная роль администратора ему не нужна. Один управляющий может обслуживать
несколько контрактов; назначение управляющим само по себе не включает его в группу.

Корпоративная ссылка заполняет код и не подтверждает вступление автоматически.
Вход и регистрация остаются штатными: корпоративный код не заменяет регистрационное
приглашение Minishop, если регистрация разрешена только по приглашению. Перед рабочей
рассылкой отдельно проверьте открытие ссылки после входа и в используемых клиентах Telegram.

## Работа с контрактом

При вступлении личный тариф и срок заменяются корпоративными без переноса остатка
оплаченных дней. Активное автопродление и незавершённые личные платежи блокируют
вступление: сначала завершите или отмените их штатными средствами Minishop.

Изменение условий создаёт новую версию и ставит операции для всех нынешних участников.
Общая сверка раз в 6 часов также исправляет отклонение срока в обе стороны. Она не
отменяет платежи и не блокирует покупки персонально. Самостоятельная оплата или
награда kiro-wheel могут временно изменить срок; сверка вернёт его к дате контракта.
В интерфейсе участника есть предупреждение и обращение в поддержку.
В покое пользовательский интерфейс не опрашивает подписку. Повторное открытие
загружает актуальные данные, подтверждение подключения заново проверяет условия.
Кнопки общего обновления и таймера следующей проверки в пользовательской странице нет.

После истечения контракта членство сохраняется, доступ ограничен его сроком; участник
видит выход к личной оплате. Продление восстанавливает корпоративные условия. Выход
или исключение сохраняет аккаунт и выдаёт новый стандартный триал ровно один раз на
операцию. При отключённом триале или неположительном сроке корпоративный доступ
отключается, пользователь может купить личную подписку.

Одноразовое приглашение даёт одно вступление; постоянное — заданное число успешных
вступлений, а не число одновременно занятых мест. Выход не возвращает использование.
Повторное вступление после исключения разрешено и расходует ещё одно использование.
Смена кода отзывает старый и начинает новый счётчик; управляющий сохраняет прежний лимит.
Уже вступивших она не исключает. С 0.1.5 новые коды и ссылки постоянно доступны
в разрешённом списке приглашений, в том числе после потери ответа. У старых кодов
сохранён только хеш: они продолжают работать, но для отображения нужен новый выпуск.

С 0.1.6 в глобальной админке можно полностью удалить код, включая использованный
или отозванный. Доступ участников сохраняется. Если есть незавершённое вступление,
сначала дождитесь его завершения, затем обновите список приглашений и удалите код.

Для полного удаления корпоративной подписки сначала исключите всех участников
и дождитесь завершения операций; исключение выдаёт стандартный триал по обычным
правилам. Затем нажмите «Удалить подписку» и подтвердите. Удаляются подписка, её
коды и история плагина. Аккаунты, личные подписки и платежи Minishop сохраняются.
Незавершённая операция блокирует удаление; её нельзя обойти стиранием записи.
Удаление отдельной подписки отличается от выключения или удаления пакета плагина.

Кнопка «Назначить управляющим» во вкладке «Участники» передаёт роль активному
участнику и снимает её с прежнего управляющего. Тариф и срок участника сохраняются;
глобальные права администратора Minishop не выдаются.

Защита Q-01 встроена в политику плагина и не имеет отдельной настройки в админке:

| Число ошибок без трёхчасового охлаждения | Разрешённая частота |
| --- | --- |
| 0–4 | 1 попытка в минуту |
| 5–8 | 1 попытка в 15 минут |
| 9 и более | 1 попытка в час |

Новые проверки кода используют **общий** бюджет на аккаунт. В 0.1.5 успешный
предпросмотр разрешает немедленное подтверждение того же кода и предложения в течение
15 минут; срок, отзыв и лимит проверяются повторно. Подмена кода или предложения
не обходит защиту. Прямое подтверждение без сохранённого просмотра учитывается как попытка.
Через 3 часа без ошибок повышенная задержка сбрасывается. Успех не стирает историю
ошибок сразу. Счётчики сохраняются при перезапуске; отдельного IP-лимита нет.
Плагин использует штатный механизм защиты Minishop, учитывает его уже действующую
блокировку промокодов и не меняет глобальные настройки обычных промокодов.

## Обновление, выключение и восстановление

Обновление устанавливается через тот же раздел **Плагины**, с проверкой версии,
хеша и прежнего издателя. Перед ним сохраните резервную копию БД и данных Minishop.
Дождитесь одинакового активного поколения backend/worker и проверьте контракты,
участников и состояние операций. Применённые миграции не запускаются повторно;
новые добавляются в конец цепочки. В текущем кандидате девять миграций.
Миграция 0005 меняет поведение удаления аккаунтов. Миграция 0006 разрешает пустой
внешний сквад в контрактах и версиях условий; существующие значения не меняются,
таблицы ядра не затрагиваются. Миграция 0007 уточняет триггер аудита собственной
таблицы контрактов: ручное снятие управляющего не помечается как удаление аккаунта.
0008 добавляет собственную таблицу успешных просмотров для немедленного подтверждения;
0009 добавляет сохраняемый текст новых кодов в собственную таблицу приглашений.
Прежние приглашения и участники сохраняются, схемы таблиц Minishop не меняются.
Обновление 0.1.5 → 0.1.6 не добавляет миграций и само ничего не удаляет.

При выключении прекращаются корпоративные UI/API, очередь и сверка. Записанные
подписки, контракты, история и приглашения сохраняются; выключение не переводит
участников на триал. До включения сроками продолжает управлять ядро, и плагин не
исправляет отклонения. Удаление выключенного пакета штатным менеджером также сохраняет
таблицы. После повторной установки состояние продолжается, а не создаётся заново.

Зависшая операция остаётся в разделе синхронизации со своим состоянием и ошибкой.
Коды диагностики в админке и ID операций сопоставляются с журналами `backend` и
`worker`; команды и состав событий приведены в [инструкции отладки](logging.md).
Проверьте worker, его поколение, доступность Minishop/панели, наличие тарифа и сквада,
а также C-01 ниже. После устранения причины worker повторит её. Не создавайте ручные
добавления дней и не удаляйте операцию/резерв: ответ панели мог потеряться после применения.
При потере ответа на создание профиля без Telegram и подтверждённого email требуется
штатная административная сверка личности; автоматическая привязка такого профиля запрещена ядром.

Тест обновления использует синтетическую следующую версию с прежней схемой.
Он не гарантирует откат произвольных будущих миграций. Для возврата после несовместимой
миграции восстанавливайте согласованную копию БД, данных и соответствующий пакет;
не редактируйте таблицу миграций вручную.
Версия 0.1.2 не поддерживает контракты с пустым внешним сквадом. После их появления
простая установка старого ZIP поверх данных 0.1.3 и новее не является безопасным откатом.

## Ограничения и удаление аккаунтов: C-01 и C-02

C-01 согласовано владельцем 2026-10-08 и сохраняется. По запросу от 2026-10-09
C-02 пересмотрено: предварительный корпоративный выход для удаления больше не нужен.

**C-01 — дополнительные гибкие квоты.** В поддерживаемую область не входят
аккаунты с действующими или будущими `FlexibleTrafficLimit`. Их квоты штатный worker
применяет поверх тарифа, а подтверждённого сервиса закрытия окон с сохранением истории
в этой ревизии нет. Плагин останавливает переход с
`minishop_corp_flexible_limits_unsupported` до изменения доступа. То же ограничение
может задержать выход/сверку, если участник купит такую квоту после вступления.

Администратор проверяет отсутствие таких окон до выдачи доступа и не назначает их
корпоративным участникам. При ошибке нужно дождаться окончания **всех** текущих и
будущих окон либо дождаться поддержанного решения со стороны Minishop. Для уже
принятой операции сохраняется повтор; если вступление ещё не было принято, его
нужно подтвердить заново с актуальным предложением. Не удаляйте историю платежей,
не правьте квоты SQL и не маскируйте ошибку прямыми изменениями Remnawave.

**C-02 — штатное удаление/объединение аккаунтов.** После обновления до 0.1.2
и применения миграции 0005 администратор может удалять участника или управляющего
обычной кнопкой Minishop. Предварительный корпоративный выход и переназначение
не требуются. Членство завершится без триала, незавершённые задания отменятся,
неиспользованные резервы кодов освободятся. История и успешные использования сохранятся.

Контракты удалённого управляющего останутся без управляющего; в редакторе появится
сообщение и возможность назначить другой существующий аккаунт. Условия и остальные
участники сохранятся. При объединении снимаются связи источника, связи цели сохраняются;
автоматического переноса корпоративной роли и членства источника нет.

Обработка работает и при выключенном или удалённом пакете: её выполняет БД, пока
таблицы плагина сохранены. Это не фоновая задача и не синхронизация с панелью.
Повторная регистрация с тем же ID не возвращает корпоративные права и старые задания.

Minishop по-прежнему удаляет профиль панели до записи БД. Сетевая ошибка или запрос
синхронизации, уже выполняющийся во время удаления, остаются границей ядра: плагин
не может отменить такой HTTP-запрос. При неполном удалении проверьте результат в
Minishop и его журнале. Исправлен именно отказ собственных связей плагина;
[решение и проверки](account-deletion.md) описывают границы подробнее.

Миграция 0005 допускает отсутствующего управляющего и состояние членства `deleted`.
Пакеты 0.1.0/0.1.1 эти состояния не понимают: не понижайте версию поверх обновлённой
БД. При необходимости возврата используйте согласованную резервную копию.
