# Членство и исполнение операций: S05–S06

Маршруты используют сессию, блокировку аккаунта и CSRF Minishop. Конверт ответов —
`{"ok": true, ...}` или `{"ok": false, "error": "ключ_локализации"}`; кеширование
запрещено. Профиль панели, ключ подписки и секрет приглашения в ответах отсутствуют.
API готовит операцию; изменение доступа выполняет worker Minishop.

## Пользователь

Базовый путь — `/api/plugins/minishop-corp`.

| Метод и путь | Результат |
| --- | --- |
| `GET /membership` | Текущее членство либо `null`, публичные условия контракта и последнее состояние операции |
| `POST /membership/confirm` | Проверка предложения, создание членства `pending`, операции и резерва приглашения |
| `POST /memberships/<membership_id>/leave` | Выход из указанного собственного членства |
| `GET /operations/<operation_id>` | Собственная операция, включая результат после выхода |

Тело подтверждения содержит `request_id` (UUID), `code` и `offer` с полями
`invitation_id`, `contract_id`, `contract_version` из предпросмотра S04. Условия доступа
клиент не задаёт. Код и версия проверяются повторно под блокировками; смена условий
до подтверждения возвращает 409, недоступный код — 400. Предпросмотр и подтверждение
делят бюджет Q-01: после предпросмотра нужно дождаться `retry_after`.

Принятый запрос возвращает 202 и `operation`. Его повтор с тем же `request_id` и
ссылкой на предложение возвращает ту же операцию с 200, в том числе после отзыва
кода или завершения членства. Это чтение принятого решения: код повторно не проверяется
и бюджет не расходуется. Повтор не создаёт членство после выхода. Для нового вступления
нужны действующее приглашение и новый UUID. Другой смысл принятого UUID даёт 409.

Q-03 проверяется до создания резерва и ещё раз исполнителем: автопродление должно
быть выключено, личные платежи завершены либо отменены средствами Minishop.
Если платёж появился уже после принятия запроса, операция ждёт в `retry`, показывая
причину; резерв сохраняется. Плагин не отменяет платежи или подписки провайдеров.

У аккаунта одно текущее членство. Пока доступ изменяется (`pending`/`leaving`),
другая операция изменения доступа возвращает 409 `minishop_corp_operation_busy`.
Нужно дождаться результата текущей операции; при длительном сбое доступна диагностика
её состояния. Это последовательное выполнение: незавершённое вступление не отменяется
новым выходом. Повтор уже принятого запроса всегда возвращает его состояние.

Выход и исключение из активного членства могут отменить ожидающую/повторяемую
операцию `reconcile`. Её старый токен отзывается, затем сохраняется новое поколение
членства и операция выхода. Если сверка уже вызывает Minishop, запрос выхода ждёт
завершения этого вызова под штатной блокировкой пользователя; после принятия выхода
старая сверка больше не может изменить доступ. Это не отменяет незавершённое вступление.

Тело выхода — `{"request_id": "<uuid>"}`. Идентификатор членства в URL защищает
от запоздалого запроса выхода после нового вступления. Завершение переводит членство
в `left`, освобождает текущую связь и оставляет историю. При исключении — `excluded`.
Окно стандартного триала фиксируется при принятии запроса; повтор не сдвигает даты.
При выключенном триале или неположительном сроке Q-02 выбирает отключение доступа.
Если триал выключили до исполнения, этот выбор сохраняется в операции и не меняется
обратно при последующем включении настройки. Личная покупка после выхода доступна.

`GET /membership` возвращает `id`, `state`, `contract`, `joined_at`, `can_leave`,
`notice`, `expiry_notice`, `operation`. У контракта только публичные поля
`id`, `name`, `ends_at`, `version`, `expired`. `notice` содержит ключ предупреждения
о самостоятельной оплате. Истечение не завершает членство и не выдаёт триал;
`expiry_notice` предлагает ждать продления либо выйти для личной оплаты.

S09 добавляет `tariff` с публичным названием и лимитами корпоративного тарифа.
Если тариф удалён из настроек Minishop, поле равно `null`; карточка и выход остаются
доступны. Секретные коды тарифов не передаются.

При отсутствии текущего членства ответ `GET /membership` также содержит
`last_departure`: последнюю успешно завершённую операцию выхода/исключения этого
аккаунта либо `null`. Это сохранённый результат операции, а не снимок сегодняшней
личной подписки. Поле операции `departure` равно `null` до подтверждённого успеха;
после выхода содержит только `kind` (`trial` или `disabled`) и `ends_at`.
Оно учитывает окончательный выбор worker по Q-02, доступно в `GET /operations/<id>`
и позволяет показать результат после перезагрузки страницы. Сырое `target` не выдаётся.

Для регистрации UI S09 `integration.views.view_policy` разрешает обычному аккаунту
`corporate-home` и `corporate-card` без требования подписки, а `corporate-manager` —
только при текущем назначении управляющим хотя бы одного контракта. Изменение
назначения учитывается при следующем запросе runtime. Проверки API действуют
независимо от видимости вкладки; сам управляющий не обязан состоять в группе.

## Управляющий и глобальный администратор

| Метод и путь | Проверка |
| --- | --- |
| `POST /api/plugins/minishop-corp/managed-contracts/<contract_id>/members/<membership_id>/exclude` | Текущий управляющий указанного контракта |
| `GET /api/plugins/minishop-corp/managed-contracts/<contract_id>/operations/<operation_id>` | Текущий управляющий указанного контракта |
| `POST /api/admin/minishop-corp/contracts/<contract_id>/members/<membership_id>/exclude` | Глобальный администратор, членство именно этого контракта |
| `GET /api/admin/minishop-corp/contracts/<contract_id>/operations/<operation_id>` | Глобальный администратор, операция именно этого контракта |

Тело исключения такое же, как у выхода. Аккаунт не удаляется. Q-04 разрешает новое
вступление после исключения по действующему коду; оно расходует новое использование.
Смена управляющего закрывает прежнему управляющему новые действия и чтение операций.
Уже принятое авторизованное действие остаётся в очереди и завершается. Управляющий
не получает глобальные права. Чужие/неизвестные ресурсы возвращают одинаковый 404.
Список участников и статистика реализованы в S07, административный UI — в
[S08](admin-ui.md); пользовательский кабинет относится к S09.

## Очередь, сбои и порядок блокировок

`minishop-corp.operations` регистрируется через `WorkerTaskSpec`. Пустая очередь
проверяется раз в 2 секунды. Исполнитель забирает одну готовую запись через
`FOR UPDATE SKIP LOCKED` и сохраняет аренду на 2 минуты отдельной транзакцией.
Истёкшая аренда допускает восстановление после рестарта. При ошибке задержка повторов
растёт от 5 секунд до 5 минут; неизвестный результат не освобождает резерв.

Перед эффектом worker блокирует штатный аккаунт, контракт, членство, приглашение и
операцию; затем проверяет токен аренды, текущий аккаунт, поколение и состояние членства.
Блокировки сохраняются во время вызова Minishop. Конкурирующий worker пропускает
занятую операцию, даже если срок аренды истёк. Старый токен не может применить доступ
после восстановления, выхода или повторного вступления.

Штатный метод выдачи триала может вызвать `rollback()`. Поэтому адаптер работает
в отдельной `AsyncSession` с savepoint на том же соединении: его откат не освобождает
внешние блокировки и не удаляет запись операции. После ошибки сохраняются `retry`
и безопасный ключ причины. Завершение фиксируется вместе с подпиской Minishop,
членством, аудитом и расходованием резерва. HTTP-изменение панели не атомарно с БД:
после потери ответа повторяется та же цель с проверкой через сервис Minishop.

После подтверждения участник уже связан с контрактом. Если до исполнения изменились
его условия, ожидающее вступление использует текущую версию под блокировкой контракта.
В target отдельно сохраняется `accepted_version` для повтора исходного запроса.
Обновление уже активных участников и единая шестичасовая задача описаны в
[сверке S06](reconciliation.md).
Выход не зависит от последующего изменения условий контракта.

Поля операции: `id`, `membership_id`, `kind`, `state`, `attempts`, `error_code`,
`next_attempt_at`, `updated_at`. `next_attempt_at` значим для `pending`/`retry`;
успех — только `succeeded`. Ошибки панели, блокировка аккаунта, Q-03 и C-01 не
выдаются за успех. Неисправимая вручную изменённая устаревшая запись не применяет
доступ; её неопределённый резерв сохраняется для диагностики.

Границы C-01 и C-02 описаны в [совместимости](minishop-compatibility.md) и
[хранилище](storage.md). API не добавляет персональный запрет покупок.

## Проверка

Интеграционные тесты используют PostgreSQL, настоящие сервисы/DAL Minishop и
HTTP-двойник внешней панели. Проверяются исходные подписки, точная дата, повторы,
потеря ответов, новый триал/выход без него, повторное вступление, Q-03, Q-01,
роли и CSRF, два worker, восстановление аренды и сохранность внешней блокировки
после штатного rollback. Основные сценарии:
[членство](../tests/integration/test_memberships.py),
[границы и конкуренция](../tests/integration/test_membership_boundaries.py),
[политики Q-02/Q-03](../tests/integration/test_membership_policies.py).
