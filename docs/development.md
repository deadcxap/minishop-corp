# Окружение разработки

Стенд S01 используется для проверки адаптера, API, фоновых операций и интерфейсов S02–S10.
Доступны админка контрактов, пользовательское вступление/выход и кабинет управляющего.
Прежний диагностический endpoint подключения возвращает `stage: scaffold`; состояние
функций отражено в плане, а UI использует предметные endpoints членства и контрактов.

## Требования и зависимости

Нужны Linux/WSL, Python 3.12, uv (проверена версия 0.11.26), Git и Docker с Compose.
Node 24 и Chromium запускаются в контейнерах; установка Node на хост не требуется.
Ревизия Minishop и образы Node/Chromium закреплены в [dev/minishop.json](../dev/minishop.json).
Образы Python, PostgreSQL 17 и Redis 7 закреплены по digest в
[Dockerfile](../dev/Dockerfile) и [Compose](../dev/compose.yaml).

По умолчанию используется соседний `../remnawave-minishop` на ревизии
`507563b06a564a26ecb10cd4c249dcd588cbff05`. Скрипты проверяют ревизию и чистоту его
Git-состояния, не переключают ветку и не меняют файлы. Чтобы использовать отдельный
checkout внутри репозитория плагина:

```bash
bash scripts/fetch-minishop.sh
export MINISHOP_SOURCE="$PWD/.local/minishop"
```

Скрипт загрузки не перезаписывает существующий checkout. Исходники всего Minishop
не входят в историю плагина. S10 дополнительно вызывает настоящую выдачу награды
из `../kiro-wheel`, подключённого только для чтения. Его ревизия закреплена в
[dev/kiro-wheel.json](../dev/kiro-wheel.json). Альтернативный checkout:

```bash
bash scripts/fetch-kiro-wheel.sh
export KIRO_WHEEL_SOURCE="$PWD/.local/kiro-wheel"
```

`integration-check.sh` проверяет ревизию и чистоту обоих репозиториев. Все тестовые
изменения, включая данные отдельных процессов для проверки перезапуска, остаются здесь.

## Установка и быстрые проверки

Все команды запускаются из корня `minishop-corp`:

```bash
bash scripts/setup.sh
bash scripts/check.sh
```

`setup.sh` устанавливает requirements закреплённого ядра и Python dev lock в `.venv`,
editable-пакет плагина и npm-зависимости через `npm ci`. Minishop предоставляет runtime
зависимости плагина; wheel не является самостоятельным приложением.
`requirements-dev.lock` учитывает ограничения версий ядра. Для намеренного обновления:

```bash
bash scripts/lock-python.sh
```

`check.sh` выполняет Ruff, строгий mypy для `backend/`, pytest, TypeScript, сборку,
DOM-тесты и проверку установки wheel с RU/EN. Mypy читает типы закреплённого ядра,
но не выдаёт проверку стороннего исходного кода за проверку самого Minishop.
Shell-скрипты проверяются отдельно:

```bash
for script in scripts/*.sh; do bash -n "$script"; done
```

Исходный UI написан на TypeScript и DOM API. Esbuild выпускает независимые ESM entry
points `frontend/dist/customer/index.js` и `frontend/dist/admin/index.js` с отдельными
CSS. Бандлы не используют внутренние компоненты Minishop; стили ограничены корнем
`.minishop-corp`. Исходники локалей едины для UI, wheel и подписанного пакета.

## Стенд с настоящим Minishop

```bash
bash scripts/stand.sh up
bash scripts/stand.sh check
bash scripts/browser-check.sh
```

`up` собирает frontend и локальный подписанный ZIP, проверяет его валидатором ядра,
создаёт контейнеры PostgreSQL/Redis и запускает штатный `plugin_launcher.py` для
backend и worker. При повторном `up` процессы перезапускаются, чтобы загрузить
обновлённый ZIP. База и реестр установленных пакетов сохраняются.

Исходники Minishop подключены к контейнерам с `:ro`, корневая файловая система
backend/worker также доступна только для чтения. Bytecode отключён. Данные, временные
файлы, логи проверок, ключ тестового издателя, ZIP и снимки экрана находятся в `.local/`.
Docker использует свой обычный служебный storage для образов и контейнеров.
PostgreSQL и Redis не публикуют порты на хост.

`check` ждёт готовности backend, создаёт синтетические аккаунты через DAL Minishop
в базе `corp_dev`, назначает тестовому администратору роль штатным сервисом и проверяет:

- анонимные запросы, разрешённый пользовательский доступ и доступ администратора;
- запрет для заблокированного и отсутствующего аккаунта, запрет админского API участнику;
- регистрацию пользовательской страницы и административного раздела в runtime API;
- выдачу обоих ESM/CSS через штатные маршруты подписанных assets;
- состояние `active` у backend и worker в одном поколении установленного пакета.

В S01 Telegram, телеметрия, резервное копирование и автопродление отключены.
Адрес Remnawave не задан, поэтому предупреждения ядра об отсутствии панели ожидаемы.
Проверка подписок и взаимодействия сервисов Minishop с тестовой панелью относится к S02.

После `check` доступны:

- `http://127.0.0.1:18081` — web API Minishop;
- `http://127.0.0.1:18082/?audience=customer&language=ru` — тестовый host пользовательского UI;
- `http://127.0.0.1:18082/?audience=admin&language=en&theme=dark` — тестовый host админского UI.

Preview загружает manifest и подписанные файлы из работающего Minishop и проксирует
только разрешённые GET-запросы с синтетическими сессиями. Это отдельная страница
разработчика; сборка всей оболочки Minishop в S01 не требуется. Параметры `audience`,
`language`, `theme` позволяют сравнить две поверхности, RU/EN и светлую/тёмную темы.
`browser-check.sh` проверяет 16 сочетаний начального UI с настоящим backend и ещё
8 сценариев управления контрактами в админке и 16 пользовательских/управленческих
сценариев с синтетическим API: вступление/выход, создание/изменение условий, коды,
отзыв/смену, исключение и диагностику. Обе локали, темы и ширины 375/1280 px
проверяются на ошибки JavaScript, управление вкладками с клавиатуры и горизонтальное
переполнение. Скриншоты сохраняются в `.local/screenshots/`.
Границы проверок описаны в [админке S08](admin-ui.md) и [кабинетах S09](customer-ui.md).
Preview-параметр `view` позволяет открыть `corporate-card`, `corporate-home` или
`corporate-manager` для тестовых сценариев; он не заменяет штатную политику видимости.

Порты можно изменить переменными `CORP_WEBAPP_PORT` и `CORP_PREVIEW_PORT` перед `up`.
Preview и API публикуются только на loopback. Тестовые пароли, фиксированный секрет сессии
и ключ локального издателя предназначены исключительно для этого стенда.

```bash
bash scripts/stand.sh logs --tail=100 backend worker
bash scripts/stand.sh ps
bash scripts/stand.sh down
```

`down` останавливает только Compose-проект `minishop-corp-dev` и сохраняет `.local/`.
Если образ уже собран и код не изменён, запуск также возможен через обычный `up`:
повторная сборка использует кеш. Рабочие боты и чужие контейнеры не затрагиваются.

## Пакет и границы совместимости

[dev/package.json](../dev/package.json) — исходная конфигурация пакета.
Скрипт [build-dev-package.py](../scripts/build-dev-package.py) добавляет версию,
runtime, ревизию ядра, хеши и подпись Ed25519. При одинаковых файлах и локальном ключе
архив не меняется. Ключ создаётся один раз в `.local/package/development.key`.
Тестовый ключ нельзя переносить на рабочий Minishop. Скрипт
[package.sh](../scripts/package.sh) собирает отдельный пакет издателя и установочный
`minishop-plugin.json`; процесс описан в [инструкции установки](installation.md).

Пакет использует Plugin API v1, frontend host API v1 и capabilities `user_ui`,
`ui_composition`. Пакет издателя требует проверенную `core_revision`, поскольку
capabilities не гарантируют совместимость внутренних сервисов. Зарегистрированы
четыре миграции, worker операций `minishop-corp.operations` и общий worker сверки
`minishop-corp.reconciliation`. Публичный Plugin API используется при регистрации;
внутренние функции авторизации и другие зависимости ядра собраны в
`backend/minishop_corp/integration/`. Их поведение проверяется на указанной
ревизии. Наличие флага `admin_authorized` обеспечивается middleware Minishop, а не UI.

## Полная оболочка Minishop

Для проверки в полной оболочке ядра:

```bash
bash scripts/core-ui-check.sh
bash scripts/stand.sh down
```

Скрипт копирует только отслеживаемые входные файлы frontend и HTML templates в
`.local/core-ui`, устанавливает закреплённые npm-зависимости там и собирает штатную
оболочку без изменения её исходников. Только каталог сгенерированных templates
накладывается на read-only mount контейнера backend. Исходники соседнего Minishop
и его Git-состояние не меняются. Chromium использует настоящие страницы, API и
подписанные assets плагина, синтетические session/CSRF cookies и выделенные аккаунты
стенда. Проверка не заменяет вход через настоящие OAuth/Telegram-провайдеры.

`core-ui-check.sh` оставляет локальный стенд работающим; `stand.sh down` его останавливает.
Обычный `stand.sh up` пересоздаёт backend без наложения полной оболочки.

## CI

[GitHub Actions](../.github/workflows/ci.yml) после push в любую ветку собирает frontend,
формирует подписанный установочный ZIP и сохраняет его как артефакт запуска на 30 дней.
Доступен также ручной `workflow_dispatch`. Зависимости подписи закреплены в
`requirements-build.txt`, зависимости frontend — в `package-lock.json`.
Minishop и kiro-wheel не скачиваются, окружение ядра не устанавливается.
Тесты, линтеры, проверки типов и стенды в Actions не запускаются.

Постоянный ключ издателя передаётся только шагу подписи через Secret
`MINISHOP_CORP_SIGNING_KEY`. Без него workflow завершится ошибкой; временный ключ
автоматически не создаётся. Настройка секрета, скачивание и установка ZIP описаны
в [инструкции установки](installation.md). Формат пакета и его ограничение по
проверенной ревизии Minishop совпадают с локальной сборкой.

Все перечисленные выше проверки остаются обязанностью локальной разработки.
Стенд `minishop-corp-package` и его данные отделены от `minishop-corp-dev`.
[Решение об изменении CI и локальные результаты](ci-packaging.md) фиксируются отдельно
от фактического запуска на GitHub; наличие workflow не подтверждает удалённый прогон.
