# Логи и отладка

Начиная с 0.1.4 сообщения плагина используют штатный Python logging Minishop и
попадают в stdout контейнеров `backend` и `worker`. Отдельных файлов или сервера
логов плагин не создаёт. Для обычной диагностики достаточно `LOG_LEVEL=INFO`.

## Где смотреть

Из каталога установленного Minishop:

```bash
docker compose logs --since=30m --timestamps backend worker | rg 'minishop_corp'
docker compose logs -f --tail=200 backend worker | rg --line-buffered 'minishop_corp'
```

Если нет `rg`, можно использовать `grep`. Для установки без Compose сообщения
находятся в журнале процессов backend/worker используемого менеджера служб.
Раздел «Логи» штатной админки Minishop 3.8.1 показывает журнал сообщений
пользователям, а не stdout и не диагностические события плагина.

## Сопоставление с интерфейсом

В административной форме ошибка API и сообщение «Аккаунт не найден» показывают
**код диагностики**.
Скопируйте его и найдите в backend-логах. Тот же код передаётся заголовком
`X-Corp-Request-ID`; штатный `X-Request-ID` ядра остаётся отдельным идентификатором.
Если запрос отклонён middleware Minishop до входа в плагин (например, CSRF или
истёкшая сессия), интерфейс использует штатный `X-Request-ID`, если ядро его выдало.
При обрыве сети до ответа кода может не быть.

События плагина записываются одной JSON-строкой после стандартного префикса Minishop:

- `account_lookup`: вид идентификатора, результат `matched`, `not_found`, `blocked`
  или `ambiguous`, внутренний ID найденного аккаунта при успехе. Сам поисковый текст
  и email не пишутся. Пустой поиск не запрашивает каталог.
- `api_request`: обработчик, HTTP-метод, статус, длительность и код ошибки;
  ошибки и изменяющие запросы видны на INFO, обычные чтения — на DEBUG.
- `operation_result`: ID операции, контракта и участника, вид действия, состояние,
  номер попытки и код ошибки после фиксации транзакции worker.
- `reconciliation_batch`: ID общего обхода и размер обработанной порции. Расписание
  остаётся одним общим обходом раз в 6 часов.

Для операции из вкладки «Синхронизация» ищите её ID в worker-логах. Операции и их
ошибки сохраняются в БД; там же есть `ext_minishop_corp_audit` с историей действий.
Аудит не заменяет технические логи: в нём нет каждого чтения или поискового промаха.

## Что сообщать при проблеме

Версия плагина и Minishop, время и действие, код диагностики либо ID операции,
соответствующие строки `minishop_corp` из backend/worker. Неожиданные исключения
плагин записывает с типом и цепочкой файлов/строк/функций, без значений локальных
переменных, текста SQL/ответов провайдера и полного текста исключения.

Полные приглашения, токены, тела запросов и поисковый текст в новые сообщения плагина
не включаются. Штатный HTTP access log Minishop может содержать query string,
включая введённый email; плагин не меняет глобальную настройку журнала ядра.
Для передачи диагностики используйте отфильтрованные сообщения плагина.
