# API контрактов: S03

Все маршруты используют штатную сессию Minishop. Для cookie-запросов изменения
действуют штатные проверки Origin и `X-CSRF-Token`; Bearer проверяется Minishop.
Блокировка аккаунта и текущая глобальная роль проверяются при запросе. Ответы плагина
имеют конверт `{"ok": true, ...}` либо `{"ok": false, "error": "ключ_локализации"}`
и `Cache-Control: private, no-store`. Ключи ошибок есть в RU/EN.

## Справочники форм: S08

Только глобальному администратору доступны `GET /api/admin/minishop-corp/options/`:

| Суффикс | Результат |
| --- | --- |
| `tariffs` | `tariffs`: period-тарифы из настроек Minishop, названия RU/EN, лимиты и `hidden`; секрет скрытого тарифа не выдаётся |
| `squad?uuid=<UUID>` | `squad`: подтверждённые Minishop UUID и имя внешнего сквада |
| `context` | `actor_user_id`: текущий администратор для изоляции черновика формы; запрос без параметров |
| `accounts?q=<ms_ID, Telegram ID, username или email>` | `accounts`: не более одного профиля, `next_page: null` |
| `accounts?user_id=<внутренний ID>` | Точное восстановление уже сохранённого назначения |

Пустой поиск возвращает пустой список. Принимаются полный публичный `ms_…`, числовой
Telegram/внутренний ID, username с необязательным `@` или email (основной либо
подтверждённый дополнительный). Используются DAL и read-only запрос модели Minishop;
каталог, поиск по части строки и пагинация отсутствуют. При совпадении числового
значения с разными аккаунтами возвращается `minishop_corp_account_ambiguous` (422).
`q` и `user_id` нельзя задавать одновременно. Заблокированные аккаунты исключаются.
Профиль содержит `minishop_id` и `telegram_id`; email и ссылки подписки не возвращаются.
Роль проверяется до чтения и после ожидания сервисов, формы не выдают управляющему
глобальных прав.

Закреплённый Minishop предоставляет получение внешнего сквада по UUID, но не каталог
внешних сквадов. Поэтому форма принимает UUID, проверяет его и показывает имя через
`get_external_squad` со штатным кешем. Собственный запрос к панели не добавляется.
Проверка при сохранении контракта остаётся обязательной независимо от предпросмотра.

## Глобальный администратор

Базовый путь — `/api/admin/minishop-corp`.

| Метод и путь | Результат |
| --- | --- |
| `GET /contracts?limit=50&after=<uuid>` | Список доступных администратору контрактов |
| `POST /contracts` | Создание контракта, 201; идентичный повтор — 200 |
| `GET /contracts/<uuid>` | Полные условия одного контракта |
| `PUT /contracts/<uuid>` | Замена условий с проверкой `expected_version` |
| `DELETE /contracts/<uuid>` | Полное удаление пустой подписки; повтор — 200 |
| `POST /contracts/<uuid>/members/<membership>/manager` | Назначить текущего активного участника управляющим; тело `{"expected_version": N}` |

Удаление разрешено только после исключения всех участников и завершения операций.
При наличии нынешнего участника, незавершённой операции или резерва сервер возвращает
`minishop_corp_contract_not_empty` (409). Под блокировкой контракта удаляются его
приглашения, предпросмотры, история членства, операций, ревизий и аудит. Таблицы
и аккаунты Minishop не изменяются, запросов к панели нет. Исчезновение контракта
останавливает доступ управляющего и будущую обработку; глобальная сверка продолжает
работать с остальными подписками. Событие удаления после commit попадает в журнал
Minishop без имени подписки или кодов. Дополнительных миграций нет.

Назначение управляющего проверяет активное членство заново под блокировками аккаунтов,
контракта и участника. Условия подписки и глобальные роли не меняются. Сохраняются новая
ревизия и аудит. Повтор с той же версией после успешного назначения возвращает 200,
если управляющий и версия соответствуют результату; дальнейшие изменения дают 409.
Старый управляющий сразу теряет доступ к этой подписке. Отдельного такого действия
в пользовательском API управляющего нет.

Полные ответы и список глобального администратора включают `member_count`: число
нынешних участников, включая ожидающих вступления/выхода и истёкшие контракты.
Бывшие участники не учитываются. Список считает участников одним пакетным запросом
по таблицам плагина, без обновления статистики или запросов во внешние сервисы.

Пример тела создания (только синтетические значения):

```json
{
  "id": "30000000-0000-4000-8000-000000000001",
  "name": "Пример организации",
  "tariff_key": "corporate-example",
  "external_squad_uuid": "20000000-0000-4000-8000-000000000001",
  "ends_at": "2030-10-01T15:42:23+03:00",
  "manager_user_id": 910001
}
```

Клиент генерирует UUID контракта один раз перед отправкой формы и сохраняет его
для повторов. Повтор после изменения условий либо с другим содержимым возвращает 409,
не создавая второй контракт. Для PUT передаются те же поля условий без `id`, плюс
`expected_version` из последнего чтения. Устаревшая версия — 409. Неизменённые условия
с актуальной версией не создают лишней ревизии. Изменение сохраняет условия, снимок новой
версии и событие журнала в одной транзакции. Потерянный ответ на PUT разрешается повторным
GET: слепая повторная запись устаревшей версии отклоняется.

`external_squad_uuid` необязателен: отсутствие поля или `null` означает отсутствие
корпоративного переопределения. При PUT `null` снимает прежний корпоративный сквад.
Пустая строка не является UUID и отклоняется. Пустое поле выбирает штатное наследование
общего внешнего сквада Minishop и снимает персональное внешнее переопределение.
Ручные внутренние сквады сохраняются.

Имя — 1–200 символов после обрезки пробелов. Тариф — существующий period-тариф,
включая скрытый. Указанный внешний сквад подтверждается штатным сервисом Minishop, который
использует свой кеш и загрузку при его отсутствии. Менеджер — существующий незаблокированный
аккаунт по внутреннему `user_id`, не Telegram ID. Пустые/неизвестные ссылки отклоняются.
Дата требует timezone и нормализуется в UTC с миллисекундами; прошедшая дата допустима.
Ответ явно содержит `expired`. Ядро возвращает `None` как для неизвестного сквада,
так и при недоступности панели; плагин не выдаёт такую ошибку за достоверное отсутствие
сквада и предлагает проверить выбор и доступность сервиса.

Неизвестные поля, неверный UUID, наивная дата и некорректные типы отклоняются (400);
недоступные ссылки — 422. Тело ограничено 16 КиБ и требует JSON. Списки отсортированы
по UUID, `limit` — 1–100; следующий `after` берётся из последней строки. Если длина
страницы равна лимиту, клиент может запросить следующую; пустая страница завершает обход.

## Управляющий и участник

Базовый путь — `/api/plugins/minishop-corp`.

| Метод и путь | Проверка |
| --- | --- |
| `GET /managed-contracts?limit=50&after=<uuid>` | Только контракты текущего управляющего |
| `GET /managed-contracts/<uuid>` | Управляющий именно этого контракта |
| `GET /contracts/<uuid>` | Текущее членство именно в этом контракте |

Возвращается только `id`, `name`, `ends_at`, `version`, `expired`. Чужой и несуществующий
контракт дают одинаковый 404. Управляющий может обслуживать несколько контрактов,
не состоя ни в одном. Назначение/смена управляющего не создаёт членство или подписку.
Новый управляющий получает доступ сразу, прежний теряет его при следующем запросе.
Управляющий и участник не получают доступ к глобальному admin API.

Эти read endpoints и сервисные проверки ролей — основа следующих этапов. Они не дают
управляющему права менять условия контракта. Административные формы и управление
подключены в [S08](admin-ui.md); пользовательский кабинет — в [S09](customer-ui.md).
Приглашения доступны через API S04,
[членство и исключение](membership-api.md) — через API S05. Сохранение новой версии
условий служит устойчивым запросом на применение активным участникам: планировщик S06
подхватывает его без ожидания общего шестичасового запуска. Состояние применения
и ошибки доступны в [API сверки](reconciliation.md); ответ PUT подтверждает сохранение
условий, но не завершение всех операций.

## Подготовка операций

`storage.operations.prepare_operation` принимает типизированный `OperationDraft`:
контракт/версию, членство/поколение, пользователя, автора, UUID повтора и целевое состояние.
Для `join`/`reconcile` хранится period-тариф, точная дата и внешний сквад; для
`leave`/`exclude` — заранее выбранное фиксированное окно нового триала или
отключение доступа по Q-02. Target вступления содержит исходную `accepted_version`.

Вызывающий сервис обязан проверить права и взять штатную блокировку аккаунта до
вызова. Подготовка блокирует контракт и членство, проверяет их актуальность, сохраняет
цель и не делает commit. Идентичный повтор возвращает исходную операцию, в том числе
завершённую; другой смысл того же ключа отклоняется. Новый запрос для бывшего участника
или старой версии не ставится в очередь. Резервы реализованы в S04, выполнение,
lease и повторы вступления/выхода — в S05. Повтор HTTP-запроса проверяет исходное
предложение отдельно от обновляемой цели ожидающего вступления.

После удаления управляющего `manager_user_id` существующего контракта равен `null`.
POST допускает отсутствие `manager_user_id` или `null`. PUT требует явного значения
поля: `null` снимает назначение, ID назначает существующий доступный аккаунт.
Без управляющего контракт доступен глобальному администратору через админку.
Миграция 0007 отличает ручное снятие от удаления аккаунта в журнале.
Удаление аккаунта само по себе не меняет
версию условий доступа: прежний снимок остаётся историей, текущая роль снимается
с отдельной записью аудита. Список участников и сверка продолжают работать.

Схема, блокировки и поведение удаления/объединения аккаунтов C-02 описаны
в [документе хранения](storage.md).
