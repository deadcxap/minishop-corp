# План реализации minishop-corp

Базовый план от 7 октября 2026 года реализует [ТЗ](specification.md).
Порядок коммитов, ветвления и проверок определён в [CONTRIBUTING.md](../CONTRIBUTING.md).
Каждый этап имеет результат и критерий завершения. Этап может состоять из нескольких
связных коммитов; один большой коммит на всю реализацию не используется.

## 1. Состояние и последовательность

Подготовлена документация. Runtime-код, стенд, тесты и сборка плагина ещё не созданы.

но готовность интеграции подтверждается только на реальных сервисах Minishop.

## 2. Исходная совместимость

При подготовке плана изучены локальные ревизии:

| Источник | Ревизия | Для чего используется |
| --- | --- | --- |
| Remnawave Minishop | `507563b06a564a26ecb10cd4c249dcd588cbff05` | Plugin API, сервисы подписок, DAL, UI host, кеш и защита кодов |
| kiro-wheel | `3c6f3c7ecf37a0847841aa6ee908c03e9a8f0992` | Пример подключения backend/frontend, миграций и поставки ZIP |

Это ориентиры исследования, а не уже проверенный диапазон поддержки плагина.
Для стенда S01 следует закрепить конкретную ревизию; изменение её во время разработки
требует повторной проверки адаптера. Все исходники соседних проектов остаются только
для чтения, а окружение и результаты располагаются внутри `minishop-corp`.

Ключевые границы, которые нужно подтвердить тестами:

| Исходник Minishop | Наблюдение и следствие для реализации |
| --- | --- |
| `backend/bot/plugins/spec.py` | Есть хуки регистрации, маршрутов, миграций и worker; текущий Plugin API — v1 |
| `docs/development/plugin-ui-composition.md` | Карточка, страницы кабинета и раздел админки добавляются без правки frontend ядра |
| `backend/bot/services/subscription_service_impl/lifecycle_switch.py` | `admin_assign` принимает скрытый тариф, но существующий метод смены требует подписку и профиль панели |
| `backend/bot/services/subscription_service_impl/lifecycle_extension.py` | `target_end_date` сохраняет максимум сроков; не использовать его как точную установку более ранней даты |
| `backend/bot/services/subscription_service_impl/trial.py` | Активация триала проверяет историю; для выхода нужен проверенный административный переход |
| `backend/db/dal/subscription_dal.py` | Есть обновление даты через DAL; нужно учесть его изменения статуса и не активировать ошибочно истёкший контракт |
| `backend/db/dal/user_panel_squad_override_dal.py` | Внешний сквад сохраняется как переопределение, которое учитывает Minishop |
| `backend/bot/services/subscription_service_impl/traffic.py` | Штатная синхронизация учитывает срок, лимиты, тег и сквады; её побочные эффекты проверяются в адаптере |
| `backend/bot/services/panel_api_resources.py` | Устройства доступны через сервис Minishop с кешем и штатной загрузкой при промахе |
| `backend/bot/services/code_attempts.py`, `backend/db/dal/security_dal.py` | Есть постоянный учёт ошибок и фиксированная блокировка; рост задержки нужно добавить политикой плагина |
| `backend/bot/plugins/extensions/jobs.py` | Есть задания с повторами и периодическим запуском; нужно проверить семантику интервала и восстановления |

Не требуется искать универсальный запрет сторонних начислений: базовый ТЗ принимает
предупреждение и последующую сверку сроков. Прямые запросы плагина к Remnawave и
патчи ядра не являются допустимым способом закрыть пробелы совместимости.

## 3. Этапы

### S00 Документация

Результат: ТЗ с критериями CORP-01–CORP-20 и вопросами Q-01–Q-04,
AGENTS.md, CONTRIBUTING.md, этот план и навигация в README.
Каждый из трёх блоков — требования, правила, план — оформляется отдельным коммитом.

Проверки: локальные ссылки, формат Markdown, согласованность последних решений,
покрытие критериев ТЗ этапами плана и `git diff --check`.

### S01 Каркас и воспроизводимый стенд

Сформировать Python-пакет `minishop_corp`, регистрацию `Plugin`, пустые собственные
маршруты и миграционную цепочку. Настроить TypeScript-сборку отдельных пользовательского
и административного ESM entry points, заготовки локалей и конфигурацию будущего пакета.
Выбрать UI-инструментарий и зафиксировать его без зависимости от непубличных компонентов ядра.

Подготовить тестовое окружение PostgreSQL и при необходимости Redis, закрепить Minishop
и изолировать данные стенда. Подключение чужих исходников — только для чтения; отключить
bytecode и любые записи кешей рядом с ними. Настроить игнорирование локальных файлов.
Добавить реальные команды проверок в CONTRIBUTING.md и минимальный CI плагина.

**Завершение:** плагин обнаруживается ядром, тестовая страница и маршрут загружаются;
backend/worker запускаются с плагином; команды проверок воспроизводимы; соседние
репозитории не получают файлов или изменений. Основа CORP-01 и CORP-20.

Предлагаемые коммиты: `build: scaffold minishop plugin`, затем
`test: add isolated minishop integration environment`.

### S02 Адаптер назначения доступа

Реализовать узкий адаптер сервисов и DAL Minishop. Зафиксировать операции чтения
доступа, назначения period-тарифа с точной датой, сохранения внешнего squad override,
штатной синхронизации и административного перехода на новый триал.

Сначала проверить переходы на фикстурах ядра: новый пользователь без панели, триал,
платная подписка, истёкшая подписка; скрытый тариф; сокращение более позднего срока;
сохранение тегов и сквадов после штатного worker Minishop. Отдельно проверить дату,
которая уже в прошлом, и восстановление доступа при продлении такого контракта.

Для повторов работать с абсолютными целевыми датами, а не повторять прибавление дней.
Проверить возврат на новый триал с сохранением истории. Не обходить отсутствие
поддерживаемого пути фиктивной оплатой, прямым клиентом панели или патчем ядра.
Неразрешённый пробел записать в документацию совместимости и не объявлять переход рабочим.

**Завершение:** тесты доказывают все перечисленные переходы через Minishop; известны
используемые внутренние методы, их побочные эффекты и проверенная ревизия. Для спорных
настроек триала и автопродления явно указаны границы до решения Q-02 и Q-03.
Покрываются интеграционные основания CORP-05, CORP-06, CORP-07 и CORP-09.

Предлагаемые коммиты: `test(integration): pin minishop entitlement contracts`,
`feat(integration): add corporate access adapter`.

### S03 Хранилище и права

Добавить собственные миграции для контрактов, членства/истории, приглашений, резервов,
операций и журнала. При проектировании проверить совместимость с удалением и объединением
аккаунтов Minishop: нельзя молча потерять роль или перенести чужое членство при смене ID.
Уточнить необходимые индексы, ограничение одного текущего членства и порядок блокировок.

Реализовать создание, чтение и изменение контракта с валидацией тарифа, внешнего сквада,
даты и существующего управляющего. Ввести серверные проверки глобального администратора,
управляющего конкретного контракта и участника. Определить версионирование условий
и интерфейс операций, используемый последующими этапами.

**Завершение:** миграции применяются с нуля и повторно; валидация не принимает неизвестные
ссылки; роли независимы от членства; запрос к чужому контракту отклоняется; конкуренция
не создаёт два текущих членства. Основа CORP-02, CORP-10 и CORP-18.

Предлагаемые коммиты: `feat(storage): add corporate contract schema`,
`feat(contracts): add contract management and scoped authorization`.

### S04 Приглашения и защита кодов

После выбора Q-01 реализовать генерацию одноразовых кодов и постоянного кода с лимитом,
ссылки, отзыв и смену кода. Использовать криптографическую случайность; не раскрывать
коды в логах. Предпросмотр, резерв активации и её окончательное расходование разделить.

Переиспользовать механизм счётчиков и блокировок Minishop; корпоративная политика
задаёт минутный лимит, ступени задержки, максимум и сброс после выбранного периода.
Глобальная защита промокодов не меняется; дополнительный IP-лимит не добавляется.
Определить сохранение состояния между процессами и сериализацию параллельных попыток.

**Завершение:** последний доступный слот не выдают двум участникам; просмотры не расходуют
код; незавершённые операции удерживают резерв; отзыв между просмотром и подтверждением
учитывается. Защита проверена с управляемым временем, параллельными запросами и рестартом;
ошибки Minishop не считаются неправильным кодом. Покрываются CORP-12, CORP-13, CORP-14.

Предлагаемые коммиты: `feat(invites): add single-use and limited reusable codes`,
`feat(invites): add persistent attempt throttling`.

### S05 Жизненный цикл членства

До реализации зависимых сценариев закрыть Q-02, Q-03 и Q-04. Добавить endpoints
предложения вступления, подтверждения, текущего членства, выхода и исключения.
Подтверждение связано с пользователем и актуальной версией предложения; одна ссылка
не назначает подписку. Для уже состоящего участника не создавать новую активацию.

Связать резерв приглашения, операцию применения и адаптер S02. Завершать вступление
после подтверждения результата Minishop. Выход и исключение должны снимать корпоративные
условия и выдавать ровно один новый стандартный триал на операцию. Не удалять аккаунт
или историю. Учесть более новое действие пользователя во время повторения старой операции.

**Завершение:** проверены сценарии без подписки, с триалом, с действующей и истёкшей
подпиской; гонка двух приглашений; повтор подтверждения/выхода; таймаут до и после
фактического применения; исключение управляющим чужого контракта запрещено. Новый
триал не получает корпоративные сквады и не продлевается повтором. CORP-04–CORP-07,
CORP-09, CORP-10, CORP-18.

Предлагаемые коммиты: `feat(membership): activate corporate access on confirmation`,
`feat(membership): restore standard trial on departure`.

### S06 Изменение условий и периодическая сверка

При сохранении новой даты, тарифа или внешнего сквада создавать операции применения
к нынешним участникам. Сохранять версию условий; повтор старой операции не должен
затереть новую. Показывать общий прогресс и отдельные ошибки без повторной выдачи доступа
тем, кто уже вышел.

Зарегистрировать фоновую сверку каждые 6 часов в worker Minishop / SDK заданий.
Сверять сроки в обе стороны, включая участников истёкших контрактов и неактивные
подписки. Обрабатывать списки порциями, координировать несколько worker, повторять сбои.
После перезапуска выполнять актуальную сверку, если очередной запуск был пропущен.

Истечение сохраняет состав группы и возможность выхода. Продление восстанавливает
доступ нынешним участникам без нового кода. Персонального запрета покупок не добавлять;
поддерживать согласованное временное отклонение даты до успешной сверки.

**Завершение:** управляемое время проверяет границу истечения и 6-часовой интервал;
два worker не дублируют операцию; выход во время сверки и новое продление защищены;
сбой одного участника не отменяет обработку остальных. CORP-15, CORP-16, CORP-17, CORP-18.

Предлагаемые коммиты: `feat(contracts): propagate contract revisions to members`,
`feat(worker): reconcile corporate expiry every six hours`.

### S07 Данные участников и API управления

Добавить пагинацию списка участников с разрешёнными полями профиля, Telegram-ссылкой,
аватаром, трафиком и фактическим/максимальным числом устройств. Источник — Minishop;
при промахе кеша вызывать его штатное обновление. Ошибки обновления отличать от нуля,
при наличии старого значения показывать его состояние. Не создавать клиент панели.

Завершить API глобального администратора и API управляющего, включая код приглашения,
состояние операций и безопасную выдачу аватаров. Типизировать ответы для UI. Исключение
и смена кода вызывают уже проверенные доменные операции S04–S06.

**Завершение:** нельзя получить участников, аватар или выполнить действие в чужом
контракте, в том числе подставив ID в URL; управляющий не получает секретов подписки.
Проверены попадание/промах кеша, недоступность Minishop, отсутствие Telegram и большие
списки с ограниченным параллелизмом. CORP-10, CORP-11.

Предлагаемые коммиты: `feat(members): expose minishop-backed member statistics`,
`feat(api): complete scoped contract administration endpoints`.

### S08 Админка магазина

Зарегистрировать раздел «Корпоративные контракты». Реализовать список и форму контракта,
выбор скрытого тарифа, внешнего сквада и управляющего, дату с явным часовым поясом.
Добавить генерацию одноразовых кодов, постоянный код с лимитом и ссылкой, отзыв/смену,
список участников с исключением, состояние применения изменений и диагностику.

Все действия используют API плагина и штатную сессию Minishop. Повторно использовать
собственные компоненты, переменные темы и локали RU/EN. Корпоративные формы не меняют
исходники или DOM чужих разделов.

**Завершение:** глобальный администратор выполняет сценарии управления из ТЗ;
состояния ожидания и ошибки показаны корректно; формы, списки и подтверждения проверены
на мобильном и настольном экранах. CORP-02, CORP-12, CORP-13, CORP-15, CORP-19.

Предлагаемый коммит: `feat(admin-ui): add corporate contract management`.
Разделять на несколько коммитов, если формы и список участников образуют самостоятельные блоки.

### S09 Кабинет участника и управляющего

Добавить карточку на главной, доступную без подписки, ввод кода и обработку ссылки.
Реализовать предложение с явной заменой текущих условий и подтверждением, состояние
операции, карточку членства, предупреждение о самостоятельной оплате и выход.

Истёкший контракт показывает выбор: ждать продления или выйти для личной оплаты.
После выхода виден результат выдачи нового триала. Отдельная вкладка управляющего
показывает его контракты и участников, позволяет исключить пользователя и сменить код,
не открывая глобальную админку.

**Завершение:** пользователь проходит вступление и выход без помощи администратора;
ошибочный/отозванный/исчерпанный код и ограничение попыток объясняются локализованно;
новый управляющий получает вкладку, бывший теряет доступ на сервере. Сценарии проверены
в RU/EN, с клавиатуры, на мобильном и настольном экранах. CORP-03, CORP-04, CORP-08,
CORP-09, CORP-10, CORP-11, CORP-13, CORP-17, CORP-19.

Предлагаемые коммиты: `feat(customer-ui): add corporate enrollment and departure`,
`feat(manager-ui): add contract member management`.

### S10 Приёмка и поставка

Прогнать все критерии CORP-01–CORP-20 на закреплённой версии Minishop. Проверить
сосуществование с kiro-wheel: начисление дней может временно изменить дату,
сверка возвращает договорной срок; исходники обоих внешних проектов не меняются.
Проверить перезапуск во время вступления и выхода, конкуренцию кодов и массовое продление.

Настроить воспроизводимую сборку пакета, генерацию manifest/хешей, подпись ключом
издателя проекта и установочный `minishop-plugin.json`. Определить размещение ZIP
с учётом игнорирования `dist/`; не коммитить приватный ключ. Проверить чистую установку,
обновление и повтор миграций, выключение/включение и сохранность данных.

Добавить инструкции установки и обновления, список проверенных версий, известные
ограничения, настройку защиты кодов и первый CHANGELOG с реально готовыми возможностями.
Объяснить, что при выключенном плагине его сверка не работает. Публичная публикация,
push и применение к рабочему боту не являются автоматической частью локальной приёмки.

**Завершение:** пакет устанавливается на чистый тестовый Minishop, все обязательные
проверки пройдены, документация соответствует поставляемому поведению. Если проверка
невозможна из-за окружения, соответствующий пункт остаётся открытым. CORP-01 и CORP-20

## 5. Ведение плана и отклонений

В начале этапа меняйте его статус на «В работе», по завершении — на «Выполнен» только
после критерия выхода. Фиксируйте проверенную версию ядра, фактические команды и результаты
в документации этапа или отчёте по соответствующему коммиту. Незавершённые подпункты
оставляйте явно отмеченными; готовность не определяется одним наличием файлов.

Каждый связный блок коммитьте отдельно с указанием этапа `Plan: Sxx` в теле сообщения.
Изменение тестов и документации, необходимое этому блоку, включайте вместе с ним.
Собственный будущий хеш коммита не нужно заранее вписывать в документ.

Новая фича вне базового плана начинается в отдельной ветке `vibe/<feature>`.
До реализации в этой ветке фиксируются отличие от ТЗ, источник решения, критерии
приёмки и влияние на этапы. Для каждого самостоятельного отклонения создаётся своя
ветка. Уточнение Q-01–Q-04 в пределах уже описанного поведения не является новой фичей;
смена самого согласованного поведения является отклонением.

Этот план не разрешает изменение соседних проектов, публикацию пакета или развёртывание
на рабочем боте. Он определяет последовательность разработки внутри `minishop-corp`.
