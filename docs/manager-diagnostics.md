# Управляющий и диагностика после рабочего теста

Запрос владельца от 9 октября 2026 года, дополнение к S03/S08/S10.
Работа выполняется в `main` по действующему указанию владельца. Статус: в работе.

## Требования и приёмка

1. Управляющий необязателен при создании и редактировании. Пустое значение оставляет
   управление глобальному администратору; назначение себе не требуется. Снятие
   управляющего отзывает его доступ, сохраняет участников и их подписки. Ввод
   непустого поиска по-прежнему требует проверки и подтверждения найденного аккаунта.
2. Поиск принимает публичный ID Minishop `ms_…`, Telegram ID, точный username/email
   и прежний внутренний числовой ID. Источник — закреплённый Minishop 3.8.1, его DAL
   и модели внутри адаптера. Пустой запрос не перечисляет пользователей. При совпадении
   числа с разными аккаунтами по `user_id` и `telegram_id` выбор не производится:
   предлагается публичный ID, username или email. Найденный профиль показывает
   настоящий ID Minishop и Telegram ID при наличии.
3. Диагностика использует штатный Python logging Minishop. Нужны результат и тип
   поиска, код запроса для сопоставления UI с backend, ошибки API и результаты
   операций worker с идентификаторами. Поисковый текст, email, тела запросов,
   приглашения и токены в сообщения плагина не включаются. Инструкция описывает
   получение backend/worker-логов и границы штатного access log ядра.

## Обнаруженные причины и изменения

- В 0.1.3 поиск чисел использовал только `get_user_by_id`, а `ms_…` попадал в поиск
  username. Штатная карточка Minishop показывает вычисляемый публичный `minishop_id`;
  Telegram ID хранится в отдельном поле. Фикстуры с равными ID этого не обнаруживали.
- Схема уже допускает `manager_user_id = NULL`, но API создания и форма запрещают его,
  а редактирование запрещает снять существующего управляющего.
- Триггер миграции 0005 трактует любой сброс управляющего как удаление аккаунта.
  Новая миграция 0007 отличит ручное снятие от штатного удаления; применённые
  миграции не меняются. Триггер и новое условие относятся только к таблице плагина.

## Проверки

- PostgreSQL и реальные сервисы Minishop: разные публичный, внутренний и Telegram ID;
  совпадения между аккаунтами, запреты и отсутствие перечисления, доступ к контрактам
  без управляющего, назначение/снятие и история удаления, обновление миграции.
- DOM/браузер: необязательное поле, подтверждение, снятие назначения, сохранение
  черновика, диагностика пустого результата и ошибок, RU/EN и размеры экранов.
- Проверка логов: идентификатор запроса/операции есть, секретных входных данных нет.
- Полный доступный набор локальных проверок и штатная установка подписанного 0.1.4.

Форма, поиск и [диагностические события](logging.md) реализованы. Проверены 26 unit-,
253 интеграционных, 43 DOM- и 51 браузерный сценарий (включая 8 в полной оболочке
Minishop с настоящим API), типы, сборка и штатный smoke Minishop. Миграция 0007
проверена на заполненной схеме 0006 с rollback; штатное удаление по-прежнему сохраняет
отдельное событие. Неожиданные ошибки API получают безопасный JSON-конверт и код
запроса; результаты операций worker журналируются после фиксации транзакции.
