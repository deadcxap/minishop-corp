# Разработка minishop-corp

Этот документ определяет архитектурные границы, проверки и порядок работы для
разработчиков и AI-агентов. Поведение продукта описано в
[ТЗ](docs/specification.md), краткие обязательные правила — в [AGENTS.md](AGENTS.md).
Последовательность и готовность этапов ведутся в [плане реализации](docs/implementation-plan.md).

Структура правил основана на подходе Remnawave Minishop: короткая точка входа для
агента и отдельный подробный документ. Правила ядра, не относящиеся к внешнему
плагину, не переносятся автоматически.

## 1. Проверки по зоне изменений

Каркас S01 использует `pytest`, `ruff`, строгий `mypy`, TypeScript и esbuild.
Проверки выбираются по зоне изменений; бизнес-сценарии добавляются вместе с
соответствующими этапами плана.

| Изменения | Проверка перед коммитом |
| --- | --- |
| Только Markdown | `git diff --check`, `git diff --cached --check`, проверка локальных ссылок и путей, чтение изменённых разделов и согласованности ТЗ с планом |
| Модель или доменная логика | Проверка типов и форматирования Python, целевые unit-тесты бизнес-правил |
| Миграции, лимиты, членство, повторы | Интеграционные тесты на PostgreSQL, включая конкуренцию, повтор миграций и откат транзакций |
| API и права | Проверка схем запросов/ответов, авторизации, CSRF штатными средствами, чужого контракта и небезопасных повторов |
| Адаптер Minishop | Контрактные и интеграционные проверки на закреплённой версии ядра с подменой внешней панели |
| Фоновые задачи | Проверки истечения, восстановления после рестарта, двух worker, выхода участника и смены версии контракта во время обработки |
| UI или локали | TypeScript-проверка, сборка, проверка полноты RU/EN, просмотр мобильного и настольного вариантов, форм и подтверждений |
| Пакет, зависимости, CI | Полный доступный набор проверок плагина, сборка и проверка установки пакета на тестовом стенде |

При изменении нескольких зон выполняются относящиеся к ним проверки. Расширяйте
прогон при общем влиянии или неясной границе изменений. Для Markdown не нужен
полный backend/frontend-прогон. Для простой обратимой правки не создавайте тесты,
которые лишь повторяют реализацию.

Команды из корня репозитория (Linux/WSL, Python 3.12, uv и Docker с Compose):

```bash
# По умолчанию читает ../remnawave-minishop; можно задать MINISHOP_SOURCE.
bash scripts/setup.sh
bash scripts/check.sh
bash scripts/integration-check.sh
```

`setup.sh` проверяет чистоту и ревизию Minishop из `dev/minishop.json`, устанавливает
зависимости ядра и `requirements-dev.lock` в `.venv`, плагин — в editable-режиме.
Node 24 запускается из контейнера, закреплённого по digest; локальный Node не нужен.
`npm ci` использует `package-lock.json`. `.local/` содержит кеши и временные данные.

`check.sh` запускает Ruff, mypy для backend плагина, Python-тесты, TypeScript,
сборку двух ESM-модулей, DOM-тесты и проверку Python wheel с локалями.
Исходники ядра доступны анализатору типов; их собственный тестовый набор не запускается.
Для обновления Python lock используйте `bash scripts/lock-python.sh`; версии
зависимостей host ограничены requirements закреплённого Minishop.

`integration-check.sh` проверяет адаптер, хранилище, гонки и API/права на настоящем
Minishop и PostgreSQL с HTTP-двойником панели. Устройство проверок и границы
совместимости описаны в [документе адаптера](docs/minishop-compatibility.md),
[схеме хранения](docs/storage.md), [API контрактов](docs/contracts-api.md),
[жизненном цикле членства](docs/membership-api.md) и
[общей сверке](docs/reconciliation.md).

Для проверки настоящего Minishop:

```bash
bash scripts/stand.sh up
bash scripts/stand.sh check
bash scripts/browser-check.sh
bash scripts/stand.sh down
```

Изоляция стенда, тестовый подписанный пакет, preview, порты и CI описаны в
[инструкции окружения](docs/development.md). Browser-проверки используют Chromium
в контейнере и подписанные ESM-файлы из работающего Minishop.

Если обязательную проверку нельзя запустить, укажите причину и оставшуюся
непроверенную границу; этап с такой обязательной проверкой не завершён.

## 2. Граница репозитория

Все изменения выполняются только внутри `minishop-corp`, включая документацию,
служебные скрипты, конфигурацию стенда, временные данные, окружения и сборочные файлы.
`remnawave-minishop` и `kiro-wheel` — источники для чтения. Не запускайте в них команды,
которые меняют Git, создают `__pycache__`, устанавливают пакеты или пишут результаты тестов.

Тестовый стенд использует закреплённый образ либо исходники Minishop с подключением
только для чтения. Рабочие каталоги контейнеров, базы и кеши размещаются в области
плагина. При импорте соседних исходников отключайте создание bytecode через
`PYTHONDONTWRITEBYTECODE=1` либо направляйте его внутрь репозитория плагина.
Сгенерированные и локальные файлы исключайте из Git при появлении соответствующего тулинга.

Не переносите исходники всего Minishop в репозиторий и не создавайте скрытый форк
как обход ограничений Plugin API. Если нужной операции нет, зафиксируйте конкретный
пробел совместимости и найдите путь через Minishop; изменение чужого проекта не
считается автоматически разрешённым продолжением задачи.

## 3. Архитектура и интеграция

Проект — внешний плагин Minishop с Python backend и отдельно собираемыми ESM-модулями
для пользователя и администратора. Используются Plugin API v1 и необходимые
capabilities текущего ядра. Поддержка версии Plugin API не гарантирует стабильность
внутренних методов Minishop: их совместимость проверяется отдельно.

Планируемое разделение кода:

| Каталог | Ответственность |
| --- | --- |
| `backend/minishop_corp/` | Регистрация плагина, контракты, приглашения, членство, права, API, фоновые операции |
| `backend/minishop_corp/integration/` | Адаптер сервисов, DAL, профилей, кеша и защиты кодов Minishop |
| `frontend/customer/` | Блок на главной, вступление, членство, выход, кабинет управляющего |
| `frontend/admin/` | Раздел глобального администратора с контрактами и операциями |
| `frontend/shared/` | Общие типы, API-клиент и собственные UI-компоненты |
| `locales/` | Базовые RU/EN-переводы |
| `tests/` | Доменные, API, интеграционные и контрактные проверки |
| `scripts/` | Локальная проверка, сборка и упаковка |
| `docs/` | ТЗ, план, решения и инструкции |

Каталоги создаются по мере появления кода. Изменение внутренней декомпозиции,
не меняющее поведение и границы, не считается новой продуктовой фичей.

### 3.1 Minishop как владелец подписки

- Получайте core-сервисы через `PluginContext` и штатный контекст приложения.
- Доменные модули плагина вызывают собственный адаптер, а не разрозненные методы ядра.
- Для изменения core-данных используйте сервисы и DAL Minishop. Собственные SQL-запросы
  и миграции изменяют только таблицы плагина. Схему, триггеры и ограничения таблиц ядра не меняйте.
- Тариф, срок и внешний squad override сначала должны быть представлены в модели
  Minishop. Синхронизацию с панелью выполняет Minishop. Прямой клиент Remnawave запрещён.
- Не подменяйте глобально сервисы, обработчики или реестры ядра. Штатная регистрация
  расширений и политик через предоставленные функции допускается.
- Не создавайте фиктивные платежи ради назначения тарифа и не запускайте платёжные
  начисления, реферальные награды или списания как побочный эффект корпоративного вступления.
- Профиль, аватары, трафик и устройства получайте через Minishop. При промахе кеша
  используйте штатное обновление. Ограничивайте параллелизм обработки больших списков.

Проверяйте обычный, скрытый и уже назначенный тарифы, новый аккаунт без профиля панели,
активную и истёкшую подписки. Различайте публичные SDK-точки и внутренние методы;
для внутренних зависимостей фиксируйте проверенную ревизию и ожидаемое поведение.

### 3.2 Сроки и триал

Храните timezone-aware UTC. Корпоративная дата — точное целевое значение, в том числе
когда оно раньше личного срока. `extend_active_subscription_days(target_end_date=...)`
в изученной версии сохраняет максимум сроков и не является универсальным setter.

Стандартный `activate_trial_subscription` проверяет историю подписок. Переход на
новый триал должен использовать проверенный административный сценарий Minishop,
сохраняющий историю и применяющий все ограничения триала. Простая смена поля provider
или удаление истории не выполняют ТЗ.

Q-02 разрешает завершить выход без триала при выключенной настройке или
неположительном сроке: корпоративный доступ отключается, личная покупка доступна.
Q-03 блокирует вступление при автопродлении/незавершённых платежах до их разрешения
средствами Minishop; проверку нужно повторять перед применением операции.
Q-04 допускает новое вступление после исключения по действующему коду.

Одна общая периодическая задача раз в 6 часов корректирует сроки нынешних участников
всех контрактов порциями, без персональных расписаний. Каждое изменение сохраняется
независимой операцией; сбой одного аккаунта не отменяет остальные. Сверка не
является запретом ручной покупки и не отменяет платежи. Не добавляйте самодельную
блокировку покупок в обход согласованного предупреждения и сверки.

### 3.3 Повторы и конкуренция

Для изменения доступа используйте явную операцию с идентификатором, целевыми условиями,
версией контракта и состоянием выполнения. Применение идемпотентно: один запрос или
повтор после таймаута не создают ещё одно вступление, начисление триала или расход кода.

Транзакция PostgreSQL не делает вызов панели атомарным. Не удаляйте сведения об операции
после неопределённого ответа; проверяйте результат через Minishop и повторяйте безопасно.
Незавершённые операции видны администраторам и переживают перезапуск процессов.

Согласуйте порядок блокировок с Minishop. На границе изменения повторно проверяйте
членство, лимит приглашения и версию контракта. Старый worker не может применить
корпоративный срок после выхода или затереть новую версию условий. Резервирование
активаций учитывает выполняющиеся операции; счётчик успешных вступлений увеличивается
после применения и не уменьшается при выходе.

### 3.4 Миграции и данные

Идентификатор плагина — `minishop-corp`, Python-пакет — `minishop_corp`.
Собственные таблицы используют `ext_minishop_corp_`, id миграций — `minishop-corp.`.
Применённые миграции append-only: их не редактируют, не перенумеровывают и не удаляют.
Повтор запуска мигратора безопасен; ограничения членства и лимитов проверяются в БД.

Используйте внутренний `user_id` Minishop как связь с аккаунтом. Telegram ID, username
и аватар могут отсутствовать или измениться. Не копируйте профиль целиком без необходимости.
Выключение плагина не должно молча удалять его таблицы или историю.

## 4. API и безопасность

Планируемые пространства маршрутов — `/api/plugins/minishop-corp/*` для кабинета и
`/api/admin/minishop-corp/*` для глобального администратора. Управляющий использует
пользовательское пространство с проверкой роли в контракте, а не глобальный admin API.

Сохраняйте конверт `{"ok": true, ...}` / `{"ok": false, "error": "..."}`.
Схемы входа и выхода типизируйте; на интеграционных границах валидируйте внешние данные.
Проверяйте сессию, блокировку аккаунта, CSRF для изменений и принадлежность ресурса.
Управляющий видит только разрешённые поля профиля и статистики своих участников.

Ссылки и start-параметры заполняют приглашение, но не подтверждают его и не являются
авторизацией. Предпросмотр ничего не меняет. При подтверждении проверяйте актуальный
код и условия, не доверяйте ранее присланным клиентом данным контракта.

Защиту от подбора стройте на механизме Minishop с корпоративной политикой минутного
лимита и роста задержки. Не меняйте глобальные параметры промокодов. Отдельный IP-лимит
плагина в базовом плане отсутствует. Счётчики постоянные и безопасные при конкуренции.
Ошибки инфраструктуры не увеличивают число неправильных кодов.

Полные коды, секреты подписок, токены сессии и ключи панели не пишутся в журналы.
Учётные данные, приватный ключ издателя и настоящие клиентские данные не входят в Git,
frontend, manifest или тестовые фикстуры.

## 5. Frontend и локализация

Исходники frontend пишутся на TypeScript и собираются в ESM согласно frontend host API.
Каркас использует TypeScript, DOM API и esbuild без UI-framework. Общие компоненты
принадлежат плагину; внутренние компоненты Svelte ядра не импортируются.

Используйте зарегистрированные страницы, слоты, `mountView` / `unmountView` и host API.
Карточка вступления должна показываться и без активной подписки. Не привязывайте её
только к условному контейнеру активного тарифа. Не изменяйте чужой DOM по селекторам.

Повторно используйте собственные компоненты форм, списков, состояний загрузки и ошибок.
Стили ограничиваются корнем плагина и используют переменные темы Minishop. Очищайте
обработчики, таймеры и порталы при размонтировании. Не теряйте введённые данные при
обычном обновлении контекста host.

Видимые строки, placeholders, подписи, aria-атрибуты и ошибки должны иметь ключи
в `locales/ru.json` и `locales/en.json`. Используйте префиксы плагина, например
`wa_minishop_corp_` и `admin_minishop_corp_`, совместимые с локализацией host.

Проверяйте мобильный и настольный экраны, подтверждения, клавиатурную навигацию,
длинные имена, пустые списки, отсутствие Telegram/аватара и недоступность статистики.

## 6. Сборка и совместимость

Manifest пакета объявляет backend entry point, frontend entry points, файлы,
Plugin API и необходимые capabilities. Подписанный ZIP и установочный
`minishop-plugin.json` формируются скриптом сборки. Не исправляйте хеши, подпись и
скомпилированные bundles вручную. Ключ издателя принадлежит этому проекту, а не примеру.

Зафиксируйте поддерживаемую версию/ревизию Minishop и проверьте установку, включение,
перезапуск, обновление миграций и работу worker. Результат прогона на одной ревизии
не объявляется поддержкой всех версий. Если внутренний метод несовместим, диагностика
должна указывать конкретную причину и не оставлять незаметно частично применённый доступ.

## 7. Git и изменения плана

Базовая ветка проекта — `main`, пока владелец не укажет другую. Плановые изменения
выполняются в текущей согласованной ветке; отдельная ветка на каждый этап не обязательна.

Каждый законченный связный блок оформляется отдельным коммитом. Не объединяйте в один
коммит независимые функции, переработку документации и несвязанный рефакторинг. Тесты,
миграции, локали и документация, необходимые одной функции, входят в её блок.
Большой этап допускает несколько последовательных коммитов с понятными результатами.

Сообщения — Conventional Commits на английском, например:

```text
feat(invites): enforce activation limits atomically

Plan: S04
Reserve invitation capacity while membership activation is pending.
```

Для плановой работы указывайте этап в теле коммита, когда его идентификатор определён.
Не добавляйте `Co-Authored-By`. Не коммитьте чужие изменения, не переписывайте историю
без запроса и не публикуйте ветку автоматически вслед за локальным коммитом.

### 7.1 Каждая фича вне плана имеет свою ветку

Отклонение — новая функция или изменение согласованного продуктового поведения
за пределами ТЗ и этапов базового плана. Примеры: резервирование личных оплаченных
дней, общий лимит мест организации, персональный запрет покупок, новый способ оплаты.
Исправление ошибки относительно ТЗ и внутренняя декомпозиция сами по себе не являются
новыми фичами.

Перед реализацией отклонения:

1. Завершите и закоммитьте независимый текущий блок, не перенося несвязанные правки.
2. Создайте отдельную ветку `vibe/<feature>` для этой фичи.
3. В документации ветки опишите требование, источник решения, отличие от базового
   плана, критерии приёмки и влияние на данные/совместимость.
4. Реализуйте фичу отдельными связными коммитами и выполните её проверки.

Разные отклоняющиеся фичи не складываются в одну общую экспериментальную ветку.
Менять ТЗ в основной ветке задним числом, чтобы скрыть отклонение, нельзя.
При включении фичи в базовую линию обновите ТЗ и план вместе с её интеграцией.
Явный запрос владельца уже разрешает работу над указанной фичей; повторное разрешение
на обычное создание её ветки и коммитов не требуется.

### 7.2 Завершение блока

Прочитайте весь diff, выполните проверки затронутых зон, обновите документацию и статус
этапа, затем создайте коммит. Этап завершён только при выполнении его критериев выхода.
